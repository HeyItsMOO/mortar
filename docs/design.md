### The Sims 4: what is left to check

The folder path and the `sims4` catalog entry are built ([architecture.md](architecture.md#games-and-the-catalog), [HUMANS.md](../HUMANS.md#adding-a-game), [sims4.md](sims4.md)). The entry is `enabled: true`; a release or published catalog carrying The Sims 4 waits on these.

- **Verify** against a real install and record in [sims4.md](sims4.md): the `Options.ini` section header and whether key names match case-insensitively, a localized Documents folder name ("Die Sims 4"), a DX9 or legacy executable, the stock `Resource.cfg` text, an EA statement of the `.ts4script` depth limit, and `gameProcesses`.
- **NOMAD-only real-install checks** (Steam under Proton, EA App on Windows): a modded profile launches with its script mods running; the game does not reset `scriptmodsenabled` in the profile's `Options.ini` copy after a restart; Tray files appear in the game's library; the player's own Mods, saves and `Options.ini` are identical after quitting.
- **Decide** whether Windows placement is fast enough to enable. Every Play places every file again (`internal/deploy/place.go`: one copy, flush and rename per file through `datadir.CopyFile`). Measured 2026-10-10 in the Windows 11 VM (4 vCPU, SATA qcow2, Defender real-time scanning on, no OneDrive sync), `MORTAR_SCALE=1 go test ./internal/loader/folder -run ThreeThousand -v`, 3,001 files, two runs each:

  | Step | Windows, 1-byte files | Windows, 512 KB files (1.35 GB) | Linux, 1-byte | Linux, 512 KB |
  | --- | --- | --- | --- | --- |
  | first sync into the profile | 10.5 s, 10.6 s | 38.1 s, 21.8 s | 1.6 s | 2.7 s |
  | place into Mods | 8.9 s, 11.4 s | 33.5 s, 23.5 s | 1.6 s | 2.8 s |
  | purge | 1.0 s, 1.1 s | 2.2 s, 2.2 s | 0.1 s | 1.1 s |

  Process CPU was about a third of the wall time; the rest is disk flush and the scanner. Options: accept it and show progress; leave files unchanged since the last Play in place (purge only what the next profile does not want); or link files where the volume allows, which needs an answer for a mod that rewrites its own file in place.
- **Measure** the same test with the Mods folder inside a signed-in OneDrive folder (`MORTAR_SCALE_MODS=<folder>`, `MORTAR_SCALE_KB=<size>`). It needs a Microsoft account, so a person runs it (the VM has OneDrive installed, signed out).

### Patreon source: research and open choice

The source is built ([architecture.md](architecture.md#games-and-the-catalog) Patreon). Research kept so it is not repeated: the public API v2 gives a patron identity and memberships only (scopes `identity`, `identity.memberships`; `campaigns.posts` serves a creator's own campaign); the documented post resource has no attachment field; rate limits are 100 requests per 2 seconds per client and a 30 minute block after 2,000 4xx answers in 10 minutes; the terms limit patrons to private, authorised use and bar sharing a creation with anyone who has not purchased it. The live probe was skipped, so the shape stands on that documentation.

- Which games list `patreon` in their catalog `sources` is decided per game, when a modder is known to ship there.

### Decided against

Do not re-propose; each rests on a measurement or a reason.

- **ModDrop as a source:** no public listing or download API (the site is a single-page app and `/api/v1/*` answers "does not exist"), so Mortar could only build a page link. SMAPI `ModDrop:N` update keys show as an unknown source.
- **Leaving files a mod writes during play shared, and never setting a leftover aside** (2026-10-10): a profile keeps what a mod writes to its own placed files ([architecture.md](architecture.md), Write-back rules). Cost: a new archive version's changed default never reaches a profile that already holds a changed copy.
- **Removing the links Vortex leaves in the game folder** after a switch to Mortar: Play is unaffected (Mortar starts SMAPI with the profile's own `--mods-path`) and the game page offers to install Mortar's SMAPI over a linked copy. Re-weigh if testers report dangling links after uninstalling Vortex.
- **Collapsing the deploy, installer, metadata-provider and framework registries into direct calls** (2026-10-06): saves about 210 lines; [AGENTS.md](../AGENTS.md) keeps registries so a game normally needs no code.
- **A file size on GitHub Browse cards** (2026-10-16): GitHub's repository search carries no release assets, so each card costs one releases call against an unauthenticated 60 requests an hour. Nexus (`fileSize` in the search) and Modrinth (one batch `/versions` call per page) carry it.
- **Steam store art lookups cached on disk** (2026-10-16): 49 of the catalog's 50 Steam games answer on the fixed `library_hero.jpg` CDN path; only Super Battle Golf needs the store lookup, once per session; every Steam image loads through `/steam-art`.
- **Deduplicating identical files across store items** (2026-10-05, a 1.6 GB store of 724 items, 50,257 files): identical files hold 76 MB, 4.7% of the store, under the 5% bar (99 MB, 6.1% counting copies inside one item); writable files barely change that.
- **Speeding up Play** (2026-10-05, 811-mod Stardew profile, direct launch in a sandbox copy): Play to game process takes 93-120 ms wall and 60-130 ms of Mortar CPU (deploy and journal included); warm pre-Play checks take 74-260 ms. A run changes the problems fingerprint and the recheck runs when the game exits, so the next Play finds it done.
- **Trimming idle memory** (2026-10-05, same profile after a full problem check): parsed Content Patcher packs (about 80 MB) are released two minutes after the last check; after 30 minutes idle the heap holds 45 MB (RSS 192 MB), the largest part being the store listing for drift checks at 13 MB, under the 50 MB bar. A loaded Thunderstore listing (Lethal Company's: 60 MiB) is dropped when unused and re-read (`internal/source/thunderstore/index.go` `listingIdle`).
- **Cutting the details panel's open further** (2026-10-06, 811-mod profile): the card grid is one grid keyed by mod id (`frontend/src/mods/ModCards.tsx` `GridWindow`), so a new column count mounts no cards: long tasks in the 400 ms after the click fell from 103-109 ms to 79-81 ms warm. The rest is the panel's own mount and the narrowed grid's relayout.
- **Cutting a Problems check after a change further** (2026-10-05, 811-mod profile): an unchanged profile is served from the findings memo (`internal/framework/contentpatcher/memo.go`), 0.03 s of Content Patcher, and a request after a restart takes 0.3 s wall. After a change only the touched targets and packs are recomputed (`internal/framework/contentpatcher/parts.go`): a one-pack edit re-checks in 0.15 s running, 0.44 s after a restart. What is left is spread thin (statting pack files 0.045 s CPU, saving memos 0.04 s); reusing pack stamps for map stats would save under 0.01 s.
- **Caching decoded PNG alpha masks for a first Problems check** (2026-10-08, 785-mod profile): a first-ever check takes 2.1 s, about 45% decoding PNG alpha (`internal/framework/contentpatcher/footprint.go` `warmOverlayImages`); every later check is about 30 ms from the memos, so the cache would save about 1 s once.
- **Speeding up cold start, idle CPU and the frontend bundle** (2026-10-08, 805-mod profile, server mode, headless Chromium): the game page with its mods shows 0.7 s after process start (0.65 s Go CPU); idle is 0.03% of a core with no window, 0.08% with one (only the 15 s network-state check is periodic); first load is 1.96 MB of JS in 56 files; reopening the Mods tab takes 120-175 ms with at most one 65 ms long task; startup reads total under 0.1 s.
- **Caching the decoded Thunderstore listing for the background mod-update check** (2026-10-08): about 1 s of CPU once, five minutes after start, decoding the cached Lethal Company listing; nothing waits on it.
