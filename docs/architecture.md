# Mortar architecture

How Mortar works: storage, profile semantics, the game catalog and its registries, trust boundaries, and the Stardew, Nexus and wire-format facts that settle questions so they are not re-litigated. Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md). Behaviour the code and its tests already state is named here by owning symbol and test, not narrated.

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile.

- **What matters:** working for personal use with a personal Nexus API key. Registering the app with Nexus is not a v1 goal.
- **Licence:** AGPL-3.0 (GPL-3.0 for the desktop app, and it also covers a hosted share service).
- **Games:** the signed catalog lists every game ([Games and the catalog](#games-and-the-catalog)); a game's `enabled` flag makes it selectable. Windows and Linux only: macOS is out (fleet CI has no macOS runners, and Wails does not cross-compile to it). Installs are found from Steam (including Flatpak Steam), GOG Galaxy and the GOG offline installer, and on Linux Heroic's GOG library, Minigalaxy, Lutris and Bottles.

**External profile import** reads r2modman, Gale, Stardrop (Stardew Valley only), Vortex and Mod Organizer 2 when their default data is present. The Profiles page's **Import…** wizard lists every detected profile; `packsvc.LocalProfiles` reads r2modman profile folders and Gale's `data.sqlite3` (read-only, pure-Go `modernc.org/sqlite`, only profiles whose game slug is the game's Thunderstore community), `migrate.Detect` reads Vortex, MO2 and Stardrop (tests: `internal/migrate`, `internal/packsvc/service_test.go`).

- Vortex and MO2 take the game's names from its catalog entry (`importIds`: `vortex` is the game extension's `GAME_ID`, `mo2` the game plugin's `GameName`); a game without `importIds` (Lethal Company: neither manager supports it) has neither.
- **Stardrop:** profiles from the platform application-data `Stardrop/Data/Profiles`; `EnabledModIds` match manifests in the configured game `Mods` folder. `PreservedModConfigs` are written under the same caps as a `.mortar` file's configs; oversize ones are listed in the preview.
- **Vortex:** profiles from its `state.v2` persistent JSON; each profile's `modState` is matched to the extracted staging folder.
- Present folders are copied into the store; missing Nexus mods enter the share-import resolver and download queue; enabled UniqueIDs with no folder are listed as **Not found in the Mods folder**.

## Stack

- **Wails v3**, upgraded one beta at a time on purpose (betas are small fixes; no date for a stable v3.0). The pin and its Go floor are in `go.mod`.
- **Frontend:** React, TypeScript and MUI on Vite (Wails' `react` template). Typed bindings from `wails3 generate bindings` into `frontend/bindings`; client state in zustand; Lingui 6 for every string, English only.
- **Go services:** each backend area the UI calls is one Wails service (`application.NewService`), so its exported methods are bound to TypeScript. Methods only Go calls carry a `//wails:ignore` doc directive, so the bindings expose only what the GUI calls.
- **Solid window:** `BackgroundTypeSolid` (`main.go`); base, tint and surfaces: [gui-design.md](gui-design.md#surfaces-and-colour). The wallpaper endpoint `/background` honours `?mode=` (`image`, `desktop`, `solid`) and answers `Cache-Control: no-store`.
- **Frameless, themed title bar:** `Frameless: true`; the app draws its own title bar marked `--wails-draggable: drag`. Measured on GNOME and KDE Plasma 6.6 (Wayland, Fedora 44): drag, edge and corner resizing, the 768x432 minimum, double-click maximise and the window buttons work; neither compositor draws a drop shadow, so the app draws a 1px border and rounded corners. Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime` or `/wails/runtime.js`).
- **Credits:** Settings › About lists bundled licences from `frontend/src/settings/generated/credits.json`, written at every frontend build by `scripts/gen-credits.ts` from `frontend/package.json` runtime dependencies and `go.mod` direct requires, plus Mortar (`LICENSE`) and the default wallpaper. SMAPI, BepInEx and the two bridges are downloaded into a profile, never bundled, so they are not listed.
- **Session-only state:** the toast history (last 200) and the Console's command history live in memory only. A toast's Undo, Redo, Show or Retry works only while that change is still the latest for the same mods. The Notifications panel's **Earlier** list is the open profile's durable `history.json` ([Profile operations](#profile-operations)).
- **Packages:** one directory per area under `internal/` (`components` catalog and signed manifest, `game`, `loader` with drivers `smapi` and `bepinex5`, `launchplan`, `gamestore`, `runtime`, `source`, `browse`, `metadata`, `host`, `pack`: [Games and the catalog](#games-and-the-catalog)); `archive` extracts zip, RAR and 7z; `configsvc`, `savesiso` ([Saves](#saves)), `syncsvc` ([Sync folder](#sync-folder)). Every game is the catalog-driven `catalogOnly` in `internal/game`; `game.Starter` starts a launch plan the way the install's store requires.

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that recursively). State is JSON written through a temp file and rename (`datadir.WriteFile`/`WriteJSON`/`WriteStream`); no database. The Nexus key is in the OS keyring. WebView2 data is `webview/`.

- **Move** (Settings › Storage): copy to a chosen empty folder (not inside the current one, not while the game runs), verify, write `data-location` in the default folder, remove the old copy, restart. The store is copied first, cloned where the filesystem can (btrfs, XFS reflink, ReFS) so shared extents stay shared, hard-linked inodes are re-linked, symlinked folders, junctions and mount points are not followed (the move logs them). Free space is estimated extent-aware and probed with a real clone or link, because FAT, exFAT and SMB count every name (`datasvc.Measure`, `internal/datasvc/usage.go`).
- **Portable mode:** a `portable` file beside the executable (symlinks resolved) puts data at `<exe dir>/data` and ignores `data-location`; decided once at start; Move is refused. The marker is ignored inside a Flatpak (`FLATPAK_ID`, or the executable under read-only `/app`) and an AppImage mount; a marker beside an executable in an unwritable folder stops the start with `datadir.PortableError` rather than quietly keeping data on the host. A portable copy has its own single-instance id (hash of its data folder). Tests: `internal/datadir/portable_test.go`.
- **Missing data folder:** a `data-location` naming a missing folder (unplugged drive) is never created. On Windows a message box offers the default location, a folder picker or quit before the window exists. Every startup failure is appended to `startup.log` in the default folder.

Files in the data folder (shapes: the named package):

- `settings.json` ([Settings file](#settings-file)); `queue.json` (without `nxm://` keys); `download-history.json` (last 1,000); `nexus-seen.json` (per mod: `newestFileUnix`, `newestChange`, `lastLookedUnix`; capped at 2,000, least recent dropped); `cache/`; `trash/`.
- `store/<game>/<key>/`: each downloaded archive, extracted once. `.complete` marks a finished extract (extracted to a temp folder, then renamed; an item without it is incomplete and an install reports it); `mortar-root` names the relative subfolder that is the mod. Keys: `nexus-<mod id>-<file id>` (a Nexus file can hold several SMAPI mods, so the key is the file), `github-<owner>-<repo>-<tag>-<asset>-<sha256 prefix>` (the hash of the exact names separates names the folding makes equal), `local-<sha256 of the archive>`, `smapi-<version>`, `bridge-<version>-<sha256 prefix>`. `store/index.json` is each item's last use (last time any `profile.json` named it); `store/.manifests/<game>/<key>.json` and `store/verify.json` are integrity records ([Store integrity](#store-integrity)).
- `profiles/<game>/<profile id>/`: `profile.json` ([below](#profilejson)) and `mods/` (the folder SMAPI is pointed at). Each entry is copied to `mods/<store key>/` as extracted, or only the `mortar-root` subtree; further files from the same Nexus page join as `extraStoreKeys` under `mods/<entry key>/<extra store key>/`, and Update, Roll back and Remove cover every store item on the entry. Extract drops `__MACOSX`, `.git` and folders holding only `Thumbs.db`.
  - **Mod-folder picker:** an archive with a `manifest.json` that SMAPI would not find asks the user for the folder that is the mod; the same picker lists variant folders when one UniqueID appears more than once. An update reuses the same-named variant of the entry it replaces and asks again when none matches.
  - **FOMOD** detection runs first (`fomod/ModuleConfig.xml`, case-insensitive, at the item root or one folder down, UTF-8 or UTF-16). The resolved files are copied instead of the raw extraction and the chosen plugin names stored on the entry as `fomod`; Update and Roll back replay them (`internal/profile/fomod.go`) and ask again when a saved choice no longer exists or the update adds an unanswered group (`internal/fomod/resolve.go` `Unanswered`).
  - `runs/`: the last 20 launches Mortar started (`index.json`; one `<id>.txt` copy of the run's SMAPI log, capped at the console's 20,000 lines of 256 bytes). A launch without mods stores none.
  - `saves/` is the profile's own Saves folder when `separateSaves` is on ([Saves](#saves)); the swap journal is `journal/<install id>-saves/saves.json`.
- `backups/<game>/`: zips of the Saves folder taken before mod updates, before Play, before a restore and on request, under the game's `backupLocation` (empty is this folder); one game's backups are never listed or restored for another.
  - A save is a folder holding a file of its own name (Stardew Valley) or, when the catalog entry lists `saveFiles` patterns, a file in the saves folder or one folder below (Lethal Company `LCSaveFile*`; Valheim `characters_local/*.fch`, `worlds_local/*.fwl` less `!*_backup_*`) plus `saveCompanions` sharing its stem (a Valheim world's `.db`). A zip holds only saves and companions under `Saves/`; a Saves folder with no save is not backed up.
  - Rotation: each kind keeps `saveBackupsKept` (1 to 50, profile-overridable) on its own, so no kind evicts another's; `scheduled` zips rotate per save against `saveBackupKeep`. A whole-Saves zip (not `manual`, not `scheduled`) under ten minutes old stands in for a new one when the Saves folder is unchanged.
  - A sibling `<stamp>.json` `{profile, kind}` records why: `update`, `restore`, `launch`, `manual` (**Back up now**, `mortar backups create <save>`; pinned) or `scheduled` (one save, in `save`); without one the zip shows as unknown.
- `downloads/<item id>.<ext>` with `<name>.resume.json` (expected size, `ETag`, source URL, checksum when sent): a failed or interrupted fetch keeps both; Cancel and Skip delete them.
- `<game>/last-played.json`: each save folder last launched with a profile (`profileId`, RFC3339 `at`), written when a run ends and SMAPI's log names the save it loaded.
- `categories/<game>.json` (custom categories; deleting one clears that override on every entry), `tools/<game>.json` (`internal/tools`: `arguments` is a JSON array, never a shell string; `{game}`, `{mods}`, `{saves}`, `{profile}` expand in arguments and working directory; launched through `os/exec` without a shell, detached), `saved-groups/<game>.json` (`internal/savedgroups`; UniqueIDs the store lacks are listed missing, not downloaded), `endorse-prompts.json` (after five completed runs with no errors from an enabled Nexus mod Mortar may prompt when `askEndorseMods` is on: [gui-design.md](gui-design.md#mods-tab)).

### Optional files

`internal/profile/overlay.go`, `overlayset.go` (tests: `overlay_test.go`, `internal/queue/overlay_test.go`). A Nexus file with no `manifest.json` anywhere and no installer (Nexus "Optional" files that swap some files of the main one) is an overlay of the profile's entry from the same Nexus mod that holds a manifest. It is its own store item and its own `profile.json` entry with no mods and no folder, `overlayOf` naming the main entry's key. Without a main entry it is refused (`NoBaseError`: "<archive> has no manifest. Install the main file of <mod> first, then this optional file goes on top of it."); an archive with no Nexus mod ID and no manifest is refused as "No SMAPI mod was found in this archive".

- **Placement**, first match wins: a single top folder named like one of the main entry's mod folders (case-insensitive); else the layout under which most of its files already exist in the main entry; else a single top folder whose children match names in a mod folder; else Mortar asks (`RemapAsk.overlay`, answered by `InstallOverlay` or the queue's `AnswerOverlay`). The answer is stored as `overlayFrom` (folder of the store item) and `overlayTo` (where in the main entry's folder).
- **Invariant:** optional files are laid over the main folder in entry order (later wins), each replaced file removed and the new name linked or cloned from the optional store item (`datadir.MaterializeFile`), so no store item is ever written. Switching one off (`overlayOff`) or removing it restores the main entry's own file for every path any optional file covered and deletes paths only optional files brought.
- **Alternatives:** optional files of one main entry replacing any of the same files (`OverlayFiles`) switch each other off in the same write when one is added or enabled. An install whose source names the file it replaces (`Source.WithReplacing`) takes the old optional entry's place, position and switch kept.
- **With the main entry:** removing it removes its optional files; updating or rolling it back takes them off first (so carry-over never sees them as user edits), swaps the version, renames their `overlayOf` and lays them over the new folder; rebuild, Restore, Revert and Undo lay them again. Mods, problems, load order and update checks see only entries with mods; drift snapshots are taken after they are laid. A profile export zip carries the main folder with them taken off and each optional store item under `overlays/<entry key>/`.

### `profile.json`

Fields and caps: `internal/profile` (`Profile`, `Entry`). Invalid `color`, `icon` or `description` are dropped on load. Rules not obvious from the structs:

- `origin` is `link`, `mortar`, `game-mods`, `copy` (with `copyOf`) or `collection`.
- `overrides` holds profile-overridable game prefs (`defaultLaunchMethod`, `showSmapiConsole`, `backupBeforePlay`, `saveBackupsKept`, `updateModsBeforePlayDefault`, `skipPlayCheck`); `settings.ResolveAt` uses the profile value, else the key's own scope, else the registry default.
- `install` and `loader` name the game install and loader the profile runs; empty means the game's selected install and primary loader. `launchPrefix` is Linux only (ignored on Windows and Steam `-applaunch`); `launchEnv` is ignored on Steam `-applaunch`; `launchPresets[]` with `defaultLaunchPreset` (empty is the profile's own settings).
- `groups` are named sets of entry keys that enable and disable together; an entry stays in its groups through Update and Roll back.
- `intentSince`, `intentOffered`: when Mortar began keeping install reasons for the profile and whether the player answered the one-time offer for older entries. The offer covers entries another switched-on mod requires, library categories (Thunderstore Libraries, Nexus Modding Tools) and sheet suppliers; a content pack stays explicit even when required (`InferImplicit` in `internal/profile/implicit.go`, `frontend/src/mods/LegacyReasonsCallout.tsx`). Matching by name keywords (Framework, Core, Compatibility) was measured on a 660-entry profile and refused: it catches patches and content as often as libraries.

`entries[]`:

- `key` is the store item in use; for an entry cut from a folder game's archive `<item>#<path>` with `item` and `file`. Mods in an entry are components: `id` (`<format>:<local>`, e.g. `smapi:Pathoschild.ContentPatcher`), version, manifest folder, `needs`, `optional`, `contentPackFor`; `disabled` lists disabled mod ids.
- `previousKey`/`previousSource`/`previousExtraStoreKeys` are the Roll back copy; on an updated archive's first entry `replaced` is the JSON of the entries it superseded. `tray`/`trayFiles` record Tray files with SHA-256.
- `implicit`: Mortar brought the entry in for another mod (resolver dependency, a Nexus link download supplying a required mod, an import entry another listed entry requires); absent means the player asked. Set at creation, copied by every path that copies an entry, changed only by Mark explicit/implicit; loader and bridge entries are always implicit. An entry with several mods shows one main mod with the entry's reason and the rest implicit; the main mod is the base the others build on (one requiring no other mod of the entry that most require, e.g. Love of Cooking under its [CP] and [EN] packs).
- `pinned`, `skipVersion`, `note` (500), `tags` (8, each 24), `categoryOverride`, `added`, `source` (the reference used in share links).

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after last use. `ProfilesWithMod` reads `profile.json` files, not the store.

**Hero cover** (`internal/profile/cover.go`, test `cover_test.go`): a picked cover is copied into the profile folder (PNG, JPEG, WebP by content, at most 16 MB; the original path is never kept). `Covers` tries in order: the picked cover (`/profile-cover/<game>/<id>`); the `picture` of the profile's Nexus entry with the highest stored `endorsementCount` (no new call); Steam art at `/steam-art/<appid>` (`game.ArtMiddleware`: cached hero, else public `library_hero.jpg`, else for newer games with hashed paths the hero or header `IStoreBrowseService/GetItems` names). The frontend moves on when one fails and shows a solid tone after the last.

## Settings file

`settings.json` has a `formatVersion` and three blocks: `global`, `sources` (per mod source id) and `games` (per game id). A key is read at the most specific scope that sets it (source, game, install, loader, profile), then broader ones, then its default (`internal/settings/scope.go`). Source-scoped keys sit in their source's block (Nexus account and `nxm` keys, `autoTrackNexus`, `verifyNexusMD5`; Thunderstore `handleLinks`); the file is read and written as the flat field list. A missing or unparseable file gives the defaults; an invalid value is replaced by the default on load and refused on write.

Each key's meaning, scope, type, default and allowed values are defined once, in code: field comments on `Settings` (`internal/settings/settings.go`) and the registry (`internal/settings/registry.go`; defaults from `Defaults()`, checked by a test). `mortar settings get` lists every key with its value.

**Export and import:** Settings › General › Settings file writes the fields in `portableFields` (`internal/settings/portable.go`) as `{"version": 1, ...}`; import (`internal/settings/import.go`) refuses any other version and applies only after a preview. Account and machine state (Nexus identity, game folders and stores, loaders, last profile and last played, dismissals, nxm handler state, LAN settings, `backgroundImage`) and `overlayToken` are never exported; the keyring is never read.

**Disk use and clean-up** (Settings › Storage; `internal/datasvc`): a background walk (no symlinks followed) of each live profile's `mods/`, store, cache, save backups, trash and space saved by sharing files (logical minus allocated size over unique inodes; omitted when not measurable). **Clean up…** previews, then deletes exactly the listed items. The keep set is `datasvc.KeepSet`, the set the startup 30-day sweep also builds (here without the grace): store items named by no live or trash profile, `previousKey`, history snapshot key, saved group, template or staged queue item. A store key a profile names after the preview is re-checked and kept. Mod pictures have no lifetime: counted, never cleaned.

### Store integrity

Installing an item records the SHA-256 and size of every file beside the store (`.manifests/<game>/<key>.json`), so hashes are never copied into a profile. `store.Verify` re-hashes and reports files missing, changed or extra. An item stored before hashes existed is baselined by its first verification, which cannot see earlier damage.

- For a Nexus item with a sign-in, verification first looks in the downloads folder for an archive of that mod whose MD5 equals the one Nexus lists; a match is extracted as an install extracts it and its hashes become the baseline, so post-install damage is found. Without a sign-in or the archive the item is baselined from its current files. GitHub and local items have no such check (a local item's key is its archive's SHA-256, which Repair uses).
- `store/verify.json` keeps each item's last verification time and verdict (`Damaged` feeds Problems).
- The background pass `storecheck.Run` (`internal/storecheck`) starts three minutes after launch, verifies items not checked in 7 days one at a time, waits while a game runs or a download or install is active, and sleeps four times each item's check time between items (about a fifth of one core). **Check store files** verifies every item now.
- **Repair** of a damaged item: the item is set aside and re-obtained from its recorded source (a local item from its archive if still in downloads; loader items `smapi-*`, `bridge-*` by reinstalling the loader); the damaged copy is put back if the queue refuses.

## Profile operations

**Materialising store items into a profile** (install, duplicate, rebuild, re-extract, update) is per file, in order, falling through on `EXDEV`/`EOPNOTSUPP`/`EINVAL`/`ERROR_INVALID_FUNCTION` (capability cached by filesystem device id): copy-on-write clone (`FICLONE`, Windows ReFS/Dev Drive block cloning, macOS `clonefile`), hardlink on one filesystem, symlink, copy (`internal/datadir/materialize.go`).

Files a mod may write use clone or copy only: `config.json` at any depth, anything under `data/` or a saves-like folder (`saves`, `save`, `savedata`), `*.mortar-old`, and text files a user might open in an editor (`.json`, `.txt`, `.ini`, `.cfg`, `.xml`, `.yaml`, `.yml`, `.toml`, `.csv`, `.tmx`, `.md`; most editors save in place). Reason: SMAPI's `helper.Data.WriteJsonFile` (`File.WriteAllText`) truncates in place, so a hard link or symlink would leak one profile's write into the store and every other profile. Drift ignores the writable paths and does not treat a linked or cloned shipped file as modified. Deleting a profile unlinks its names and never removes store files.

**Operations** (each is a method of `internal/profile` `Store` or a service named below; the cited tests state the edge cases):

- **Toggle:** rename the folder holding the mod's `manifest.json` with a leading dot (SMAPI skips it; measured) and record it in `disabled`. Enabling a mod whose required dependencies are present but disabled enables them in the same write; optional ones are left alone. Programs can create leading-dot names on NTFS, so the root-manifest folder is found by key with or without the dot. Bulk operations are one `profile.json` write under the running-game lock (`enable.go`, `enable_test.go`).
- **Duplicate** clones or copies `mods/` as is (never hardlink or symlink, so an in-place write cannot leak into the source); origin `copy`. **Delete** moves to `trash/` for `trashRetentionDays` (startup deletes older); `Purge` and `PurgeTrash` refuse a symlink (`trash.go`).
- **Damaged profile:** an unreadable `profile.json` is listed by `ListDamaged` (Profiles page, `mortar profiles`) and skipped by `List` and `StoreKeys`, so one corrupt file does not stop collection. **Repair** (`mortar profile repair`, `repair.go`) rebuilds it from the latest readable history snapshot, leaves `mods/`, renames the broken file to `profile.json.damaged-<timestamp>` (Undo restores it); refused with no snapshot.
- **Import from the game's Mods folder** (`import.go`, `import_loose.go`, `import_test.go`): scans one level of `<game>/Mods` as SMAPI does. Each folder enters the store through the dropped-folder path (hashed-folder install, dedup by content, `UpdateKeys` as Nexus or GitHub source); dot-prefixed folders land disabled; the game folder is never written; result is profile "Imported mods", origin `game-mods`. Trap: a symlink-deploying manager (Vortex links each file from staging) imports as the files the links point to (`datadir.CopyTreeResolvingLinks`), while the store otherwise refuses links that leave a folder.
- **Move from the game's Mods folder** and **compare and sync** (`gamemods.go`, `gamemods_test.go`: `NewGameModsFolders`, `MoveGameModsFolders`, `GameModsDiff`, `SyncGameModsFolders`): copy as Import does, then delete the folder by renaming it aside first (so a file held open leaves it whole); matching is by UniqueID, case-insensitive; refused while any game process is up (`Store.GameRunning`); dismissed folders are kept in `dismissed` under `gameMods:<game>`; progress event `profile:game-mods-progress`.
- **Dot-hidden mods:** a dot-prefixed folder inside an entry that Mortar did not add hides every mod under it from SMAPI; with per-game `showDotHiddenMods` on, `DotHiddenMods` lists them and `UnhideMod` strips the dots (`dothidden.go`, `dothidden_test.go`). **Extra mods folder** (`extraModsFolder`): `InstallExtraFolderMod` installs one top-level folder through the dropped-folder path; only a direct, real child is accepted; the folder is never written.
- **Outside edits** (`drift.go`, `drift_test.go`): `mods-snapshot.json` beside `profile.json` is a cheap fingerprint of each entry folder (top-level name, file count, total size, newest mtime; skipping `config.json`, `*.mortar-old`, `data/`, saves-like folders and other files update carry-over treats as user- or mod-written). On profile load and window refocus (debounced) the live `mods/` tree is compared to it and to `profile.json`; a first scan with no snapshot records the tree and reports nothing. Findings show on the Problems bar with Adopt, Remove, Restore, Forget, Keep and Revert actions.
- **Compare:** `Diff` matches user mods of two profiles by UniqueID (bundled omitted); `CopyMods` copies through `AddEntry` (store item already on disk; no download); **Match versions** switches differing entries through `UpdateEntries`, one atomic change (a failure undoes every swap; one history event). A running game locks the destination. UI: [gui-design.md](gui-design.md#profile-management).
- **Saved groups and templates:** `SaveGroup` snapshots a group's mods with store keys, sources, install reasons and optional files. `Apply` copies missing store items in and creates a group, in one history batch (`profile.Store.AddGroup`). Templates (`templates/<game>.json`, `internal/templates`; their `entryKey`s are in the store keep set) add game settings, launch options/prefix/env, overrides and presets. `ApplyTemplate` never removes the profile's own mods, skips a store entry already held or the same UniqueID under another entry, takes `profile.Store.Baseline` first and returns an `Undo`; `PreviewApplyTemplate` returns the split and `missing` store items (`internal/templates/apply.go`, `templates_test.go`).
- **Back up and restore a file** (`internal/packsvc/backup.go`, `backup_test.go`; `profile backup`/`profile restore`): one zip with `backup.json` (format version, game, every setting and entry, a content hash per carried store item), history, config files and cover under `files/`, the profile's own saves under `saves/` and each mod's store item under `store/<key>/`. **Include mod files** (`--no-mods` clears it) carries every mod so the file restores offline; off, only mods no source can download again; bundled entries and rollback copies are never packed. Restore makes a new profile named with `UniqueName`, never overwriting; store items go in only when their hash matches. Restore also reads the old profile zip (`profile.json` plus `mortar-export.json`, a SHA-256 per file), which nothing writes: it needs the game from the caller, extracts with the archive caps, checks every hash, refuses paths leaving the zip and ignores an absolute `cover`; `backup.json` tells the two apart.
- **Typed config editing** (`internal/configsvc`, `FuzzCfgSetKeepsOtherLines`): a mod's config files are its SMAPI `config.json` and the `.cfg` files in `<profile>/BepInEx/config` whose file name or `## Plugin GUID:` header matches the mod id (empty id lists every `.cfg`). `Schema` returns sections of typed entries (`bool`, `int`, `float`, `enum`, `string`, `color`, `list`) with value, default, description, range, acceptable values and a `flags` marker for comma-combined enums.
  - `.cfg` is read in BepInEx's layout (`## description`, `# Setting type:`, `# Default value:`, `# Acceptable values:`, `# Acceptable value range:`, `Key = value` under `[Section]`); `Set` rewrites only that entry's line.
  - `config.json` is flattened in file order (nested object is a section named by its dotted path, an array a `list` of compact JSON, a `#rrggbb`/`#rrggbbaa` string a `color`). Writes go through the profile's `SetJSON` (path refused if it leaves the mod folder; key order, types and unknown fields kept). Where the SMAPI Bridge captured a mod's GMCM options, their labels and ranges come with the entries ([Generic Mod Config Menu](#generic-mod-config-menu)).
  - Every write fails while the profile's game launches or runs; a `.cfg` name is only a bare file name inside the profile's BepInEx config folder.
- **Pin and skip:** **Pin this version** is `pinned` (optional `pinReason`; CLI `keep`/`unkeep`) and writes a `pinned` history event. A pinned entry is offered no update; `skipVersion` hides that exact newer version until a later one appears. Both drop out of the update count, Update review and Update all.
- **Update checks** (`internal/control/updates_apply.go`, `internal/profile/service_update.go`): at startup (`checkModUpdatesOnStart`) and every `updateCheckIntervalMinutes` for the open profile; SMAPI API answers are cached an hour per profile fingerprint; F5 or the app menu's check bypasses the cache (`CheckUpdatesNow`). SMAPI's API is asked 100 mods per request; for the mods it flags, Nexus GraphQL v2 is asked once for all their current file lists (aliased `modFiles` queries, 50 mods per request; signed in only). An update is real when a newer non-archived file with the same display name exists or the installed file's version is below SMAPI's; an unbumped manifest inside the newest file is not offered. Signed out or on failure the mod dataset's file list decides the same way, and a dataset page listing nothing newer than SMAPI's version is treated as stale. The same toggle starts a background pass 5 minutes after open, then every 4 hours, over every installed game's profiles; a desktop notification "Mod updates available" names the profile with the largest increase over the last notified count.
- **Change history** (`internal/profile/history.go`, `historystorage.go`): events in `history.json`, capped by `historyEventsKept` (20 to 2000).
  - Each distinct entry snapshot is gzipped to `snapshots/<sha256>.json.gz` (about a seventh of plain JSON); snapshot and `history-files/` bytes are not capped. Events store added/removed/updated counts when recorded so listing reads only `history.json`.
  - An event also keeps the profile's settings (`ProfileState`: groups, loader, game install, separate saves, launch options, prefix, env, presets, per-profile overrides, collection); name, notes, colour, cover and profile order are not history. A `config.json` Mortar writes records a `config` event after one capturing the file as it was; Revert rolls configs back only when every event since the target is such an edit. Invariant: every profile mutation records an event and undoes exactly (`TestEveryProfileChangeRecordsAnEventAndUndoesExactly`, `undo_coverage_test.go`).
  - Export zips leave out `history.json`, `snapshots/`, `history-files/`, `runs/`. `RecentHistory` (`mortar history --all`) merges every non-damaged profile of the game, newest first, capped at 50.
- **Update or roll back** an entry (`internal/profile/update.go`, tests `update_test.go`, `syncrules_test.go`): copy the target version from the store into a fresh folder, then carry over what the mod or user wrote by comparing three copies of each file (the profile's, the store's copy of the current version, the target). Disabled folders keep their leading dot; then `key` and `previousKey` swap. Before updating a profile the Saves folder is zipped into `backups/`.
  - A file only the profile has is carried over. A file the profile changed is carried over when the target ships it unchanged; when the target changed it too the target wins and the profile's copy is kept as `<name>.mortar-old`.
  - When the target manifest sets `DeleteOldVersion` (Stardrop's name, read case-insensitively like other manifest keys), carry-over applies only to user-written files such as `config.json`, and old files are never asked about.
  - A file the profile holds unchanged that the target no longer ships follows per-game `oldFilesOnUpdate` (`delete`, `keep`, `ask`); `ask` moves it to `old-files/<new key>/<UniqueID>/<path>` beside `profile.json` (`oldfiles.go`: `PendingOldFiles`, `ResolveOldFiles`, `TrashOldFiles`, tests in `oldfiles_test.go`, `syncrules_test.go`).

## Command line

Mortar is GUI-first: the CLI exposes only what the window can already do, and a new capability lands in the window first. Verbs: [HUMANS.md](../HUMANS.md#command-line).

- `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path or `--play=<game>/<profile>` is a window launch. Output flags (`--json`, `-v`, `--verbose`) may precede the verb (`leadingFlags`). Under `--json` a failure is `{error, kind, code}` on stderr plus `detail` (typed fields of a `usererr.Detailer`) when the app sent one.
- `--play` ids may not contain `/`, `\`, space or quotes; a running instance receives it as a second instance (`play:requested`) and Play takes the usual path, warnings included.
- **Play mode** (`--play=<game>/<profile> --steam-session`: an Add to Steam shortcut while Mortar is closed, Steam's Game Mode on the Deck; `shortcut.Service.Start`, `frontend/src/launch/playMode.ts`): the window starts hidden and renders only the launch layer; Play takes the usual path with every pre-Play check. A blocking check shows the window at 560x480 holding only that dialog with larger touch/gamepad targets; any other way out leaves play mode and opens the full window as a normal session. The `onPlay` window setting does nothing in play mode.
  - `main` quits once the played game has been Running and is Idle again, after purge and settings restore, so Steam counts playtime from Mortar's own process. If a Mortar already answers on the control channel, a `--steam-session` start does not hand off as a second instance (that exits at once): it sends `play.request` over the control channel before `application.New`, then `shortcut.Follow` (`internal/shortcut/follow.go`) polls `status` until the game has been active and is idle again; a game not started within 15 minutes ends the wait.
- **Control channel** (`internal/control`; the CLI is a client of the running app): the app listens on `127.0.0.1` on an OS-chosen port and writes `control.json` (`port`, random 32-byte `token`, `pid`, `version`, `protocol`; 0600) in the data folder, removed on exit only while still that instance's file. Each connection carries one JSON request line (`token`, `method`, `params`) and one reply line (`result`/`error`); the token is compared in constant time. Methods run on the app's own services, so window and CLI never write the data folder at once; a change emits `profiles:changed` with the game id (`control_test.go`).
  - `controlwire.Protocol` (1): the CLI calls `hello` first and fails with "this mortar CLI speaks control protocol N, the app speaks M" on mismatch.
  - A start finding another Mortar answering `hello` with the token in `control.json` waits five seconds for it to exit, then stops before it rotates the log or touches data. A server build refuses to start on the account's own data unless `MORTAR_SERVER_REAL_DATA=1`; `scripts/selftest.sh` gives it a sandbox `HOME`. Without `WAILS_SERVER_PORT` it takes a free loopback port rather than Wails' default 8080; the desktop app opens no HTTP port.
- `launch` detaches the game from the request (`context.WithoutCancel`). With `updateModsBeforePlayDefault` it first queues the updates needing no choice (`queueUpdates`, `internal/control/methods.go`) and waits up to five minutes; a failed update stops the launch, a download a free Nexus account must click through does not. `install` queues the required mods its new mods lack when `missingRequirements` resolves to downloading (`queueMissing`); with the setting on asking it queues nothing. On Windows the GUI-subsystem exe attaches to its parent console (`AttachConsole`) unless output is redirected.

## Trust boundaries

Everything from outside is untrusted: links, `.mortar` files, archives, API responses. Share links and `.mortar` files have their own caps in [Sharing](#sharing). Threat model and the test for each input: [security.md](security.md).

- Extraction keeps every entry inside its destination; caps each entry at 256 MiB, decoder dictionaries and PPMd memory at 256 MiB, the archive at 2 GiB extracted and 20,000 entries; rejects symlink entries, Windows reserved names (`CON`, `NUL`, ...), `:` in names and names differing only by case.
- An `nxm://` link is taken only as `nxm://stardewvalley/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`, unexpired, for the signed-in account's `user_id`; anything else is refused with the reason. A link Mortar was not waiting for asks which profile it is for before anything downloads.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile. Failures reaching the user are classified in `internal/usererr` (not found, busy, network, permission, disk full, damaged, invalid). Go wraps the cause as `[kind] message`; the window (`errorMessage` in `frontend/src/toasts/report.ts`) and the CLI (`Sentence` in `internal/cli`) map the kind to the same English sentence, with the cause in a Details tooltip or under `--json`/`-v`.

- **A mod source unreachable:** `internal/netstate` records per source (smapi.io's update API included) whether its last real request hit a network error (DNS, timeout, refused); a merely bad answer leaves state alone, and Go emits `netstate:changed` on a flip. Unreachable sources are probed every five minutes. A banner names each down source and network actions needing one are disabled (`frontend/src/shell/OfflineBanner.tsx`, `OfflineGate.tsx`). Trap: SMAPI's API or the dataset unreachable degrades and never blocks: update checks show "unknown", dependencies are checked after download.
- **Archive formats** (`internal/archive`, `formats.go`, `stream.go`): zip, RAR, 7z, tar and gzip, xz, lzma, zstd, bzip2 streams, found by magic bytes, never extension (`archive.Extensions` is only what pickers, drop, the downloads watcher and source name handling accept). A compressed stream whose payload has a `ustar` header is read as a tar (a v7 tar without `ustar` is not recognised); any other compressed stream is one file named from the archive's name minus its suffix. A classic `.lzma` stream has no magic, so it is recognised by a valid properties byte, power-of-two dictionary size and sane length. Tar entries pass the zip guards (symlinks and hardlinks refused as `ErrLink`, devices, pipes and sparse files as `ErrSpecialFile`). Libraries: stdlib `compress/gzip`, `compress/bzip2`, `github.com/ulikunitz/xz`, `github.com/klauspost/compress/zstd`. The download queue keeps a bare compressed file as `<id>~~<original name>` (`archive.SavedName`; read back by `archive.SavedID`) so the extracted file takes its real name; a dragged-in file and a LAN transfer keep their names.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves in only when every entry passed its checksum (CRC32 in zip, RAR, 7z; gzip and zstd check their own); failure deletes the temp folder and the item can be retried. **Disk full** fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename and startup removes leftover temp folders. `crash.log` is capped at startup once `crash.seen` covers it. A `mods/` folder deleted outside Mortar is rebuilt from the store from `profile.json`.
- **Startup repairs are reported once:** what startup repaired itself is collected by `internal/tidy` and logged; when anything was repaired the window shows one info notification, "Mortar tidied up N things", with details under **Details**.

## Tests

Go tests run against local HTTP test servers replaying recorded Nexus, SMAPI API and dataset responses, inside the 10 s warm gate budget. Recordings are scrubbed before commit: `users/validate.json` returns the account's name and email, so fixtures carry placeholder account fields. An opt-in smoke test copies a real Stardew install to scratch, installs SMAPI with `--no-prompt`, launches a profile and reads `SMAPI-latest.txt` for the loaded mods. Tests must set `XDG_DATA_HOME` (or `LOCALAPPDATA` on Windows) to a directory under `os.TempDir()`; `datadir.Dir` refuses any other location while `testing.Testing()` is true.

## Games and the catalog

Everything that can be data is catalog data; code exists only where behaviour differs, as a driver found through a registry. Adding to each registry: [HUMANS.md](../HUMANS.md#adding-a-game). Catalog entries are hand-curated; there are no user-defined games. Each registry below is a package under `internal/`; its driver list, capability interfaces and per-driver tests are in the package, not restated here.

- **Catalog:** `internal/components` holds `GameInfo` entries in the signed component manifest (`GameInfo.Validate` guards the shape; `TestEveryCatalogReferenceResolves` checks every source, loader, metadata id, store field, path role and path token resolves). `game.Catalog()` returns the verified manifest's games when it lists any, else the bundled ones. Optional blocks an older Mortar ignores (so the v2 schema is unchanged): `graphics` (the graphics API choices Play offers) and `knownBroken` (`{id, versions, reason, replacement}`, `versions` space-separated constraints such as `>=1.0 <1.5`; ships empty).
- **Stores** (`internal/gamestore`): one driver per store key in the catalog's `stores` (`steam`, `gog`, `lutris`, `bottles`, `ea`, `epic`, `xbox`, `standalone`, `flatpak`), run only for games naming its key. `flatpak` reads the app's current deployment in user and system installations, with `{xdgConfig}`/`{xdgData}` under `~/.var/app/<app>` and start `flatpak run <app>`. A native Linux build starts through `linuxStart`, else `linuxMarker`. A user-chosen folder wins over discovery (origin `folder`). `GameInfo.MarkerDir` is the folder under the install root holding the marker (The Sims 4: `Game/Bin`); the install folder stays the root.
- **Installs and runtime** (`internal/game/install.go`, `internal/runtime`): an install is a store and a folder with a stable id, a platform (an `.exe` marker is a Windows build) and a runtime:

  | Runtime | Claims | Path template resolves in | Start |
  | --- | --- | --- | --- |
  | `native` | native builds | the host's folders | direct |
  | `proton` | a Steam Windows build on Linux | its `compatdata` prefix | Steam |
  | `wine-prefix` | a Windows build in a Bottles bottle (install carries `prefix`) | the bottle's `drive_c/users/<user>` | `bottles-cli run -b <bottle> -e <exe> -- <args>` (`flatpak run --command=bottles-cli com.usebottles.bottles` for Flatpak Bottles) |
  | `mortar-proton` | any other Windows build on Linux (chosen folder, Heroic, Lutris, EA) | a prefix Mortar keeps per game, `<data>/prefixes/<game>/pfx` | as Heroic and Lutris start Proton outside Steam: `<proton>/proton waitforexitandrun <exe>` with `STEAM_COMPAT_DATA_PATH` (that folder) and `STEAM_COMPAT_CLIENT_INSTALL_PATH` (the Steam with the build) |

  `runtime.FindProton` picks the build (rules and tests: `internal/runtime/mortarproton.go`, `mortarproton_test.go`); Flatpak Steam's builds need its runtime and are excluded. A loader's DLL overrides reach the prefix as `WINEDLLOVERRIDES`, so the first start, before Proton has made the prefix, loads them.
- **Sources** (`internal/source`): a driver registers itself (`source/all` imports them) and implements `Source` plus optional capabilities found by type assertion (`Searcher`, `Categorizer`, `Gated`, `Schemer`, `Hoster`, `LinkOptIn`, `Sorter`, `ItemLister`). A scheme is claimed from the system only when the source's choice allows (`source.SetHandleLinks`). Drivers: Nexus (GraphQL search, `nxm`), GitHub, Thunderstore, Modrinth, CurseForge, itch.io, Patreon, Vintage Story Mod DB ([vintage-story.md](vintage-story.md#sources)). A `Gated` source says through `Unavailable()` what the user must set up first; the window greys its chip with that reason and an `all` search leaves it out.
- **Browse** (`internal/browse`; tests `merge_test.go`, `sort_test.go`, `flags_test.go`, `installed_test.go`): a search names one source or `all`, which asks every searchable source and interleaves the answers; failed sources are listed in `Failed` and only all failing is an error. A page holds `source.PageSize` (20) hits.
  - **Merging** (`mergeSame`): hits of one mod from different sources fold into one card on package identity or an explicit link, never names (loader plugin id or UniqueID, the GitHub repository a hit links, the Thunderstore package its summary points at). The card is the earliest source in the player's `SourceOrder`; the others are its `Alts`.
  - **Sort** is a `source.Sort*` value; a source lists the sorts its API honours through `source.Sorter` and nothing is sorted client-side within one source. Under `all` only `MergedSorts` (`downloads`, `updated`) are offered, because Modrinth and GitHub cannot honour name or newest; `sortMerged` places a hit with no value (GitHub has no download count) after every hit with one.
  - Empty search text lists each source's top mods, reused ten minutes (`searchCached`). `Categories(game, source)` is cached a day; Nexus serves categories only to a signed-in account. `Adult` hits are dropped unless `showAdultContent` is on.
  - **In-profile matcher** (`internal/browse/installed.go`): `Hold` decides whether a card is in the open profile from each entry's own source and the `UpdateKeys` of every installed manifest, so an archive-installed mod matches the page its manifest names; the bundled loader companions report `Bundled` ("Installed by Mortar").
- **Thunderstore** (`internal/source/thunderstore`): search reads the community's chunked package index (`/c/<key>/api/v1/package-listing-index/`, a gzip list of chunk URLs). The slimmed listing is cached at `<datadir>/cache/thunderstore/<key>-<hash of the index blob>.json`, used an hour without asking; then only the index blob is fetched and chunks only when its hash changed; a failed fetch falls back to the cache. Deprecated packages are not searchable but still resolve as dependencies; NSFW ones are `Adult`. `ParseLink` reads `ror2mm://v1/install/thunderstore.io/<namespace>/<name>/<version>/`.
  - `Closure` treats a dependency's pinned version as a minimum and installs the newest, as r2modman does, unless a root of the same request names that package at an exact version (`closure_test.go`). Managers a community lists as packages (r2modman, Gale) are programs: search omits them and a mod depending on one installs without it.
- **Gated sources** (`modrinth`, `curseforge`, `itch` under `internal/source/`; shipped games list only CurseForge, for Stardew Valley) install through the queue's direct path (`queue.ResolveDirect`, `expandDirect`): the request and its required dependencies resolve first, each project once and at most 16 deep; a `sha512:` digest is verified after download. An entry's source kind is `modrinth`, `curseforge` or `itch` with the project or game id as its name.
  - **Modrinth:** public API v2 (`https://api.modrinth.com/v2`) with the `User-Agent` Modrinth requires (`Rethunk-Tech/mortar/<version> (+https://mortar.rethunk.tech)`). A game's source `key` is a facet (`categories:fabric`, `project_type:mod`; a bare word is a category). `Resolve` takes the newest (or named) version's primary file with the published SHA-512; only `required` dependencies are followed. The queue holds Modrinth fetches to 4 at once, started 5 a second after a burst of 10 (Modrinth's 300 requests a minute per address).
  - **CurseForge:** Core API v1 (`https://api.curseforge.com/v1`) with Mortar's own key in `x-api-key`, never in an address or log: `-X .../internal/source/curseforge.apiKey=...` at release build, else `MORTAR_CURSEFORGE_KEY` for dev builds; with neither the source is `Gated` ("this build has no CurseForge API key"). A game's source `gameId` is CurseForge's game id and `key` its "Mods" class id (Stardew Valley: 669 and 4643; `/games` lists neither Lethal Company nor Valheim). A file has no version number: its version is its display name and an update names the file by id. The digest is `sha1:<hex>`; the queue does not verify it because the lint bans weak hashes. Only `RequiredDependency` (relation 3) is followed. When an author forbids distribution (`allowModDistribution` false, or no `downloadUrl` and a refused `download-url`) the driver never builds a CDN address: the request fails with `NotDistributableError` and the queue opens the mod's page (`/projects/<id>`). The queue holds CurseForge fetches to 3 at once.
    - **Classes:** a game source may list `classes` (class ids a search covers; must include its `key`). A multi-class search merges by the query's sort and stops at 1,000 results; a class that errors does not fail the search while another answers (`Page.Failed`), and such a page is not cached (`classes_test.go`).
  - **itch.io:** server-side API (`https://itch.io/api/1/x`) with the player's own key in `Authorization`, never in an address (an error quoting the address cannot leak it). The key is in the OS keyring under `itch`; `itch.Service.SignIn` tests it, stores it and keeps only the account name (`itchName`) in settings. The source `key` is searched as a keyword (no tag filter); the API has no sort and no total, so `Total` counts this page plus one when the page is full. `Resolve` picks the upload by id or file name, else the first not flagged demo or soundtrack, and asks itch.io for its time-limited download address; no dependencies.
  - **GitHub and Nexus sorts:** GitHub repository search `sort` is stars, forks, updated (no downloads, name, created); Nexus `ModsSort` endorsements, downloads, updatedAt, createdAt, name.
- **Handoff sources** (no search, download or update check): the player saves the file from the site, the Downloads watcher picks it up and `archivesvc.InstallHandoffDownload` adds it; `archivesvc.HandoffPage` gives the window the address. A share ref carries the id and no file; the receiver's preview lists it unavailable with its page until their profile holds a file from it.

  | | Patreon (`internal/source/patreon`) | itch.io page (`internal/source/itch`, `Handoff` beside `Download`) |
  | --- | --- | --- |
  | Why | no API for a post's files and its terms bar automated access | catalog names `{"id": "itch"}` with no key |
  | Input | `ParsePostURL`: https, `patreon.com`/`www.patreon.com`, `/posts/<id>` or `/posts/<slug>-<id>` | `ParsePageURL`: https, host `<user>.itch.io`, one game slug, as `user/game` |
  | Entry source | `profile.KindPatreon`, the post id | `profile.KindItch`, the page name |
  | Share ref | `patreon: <id>`, `sharesvc.ReasonPatreon` | `itch: <user/game>`, `sharesvc.ReasonItch` |
- **Metadata** (`internal/metadata`): the catalog's `metadata` ids resolve to providers with capabilities `Updates`, `Status`, `Dataset`; a game without one gets none. **Hosts** (`internal/host`): `host.GitHub` fetches release assets (using the user's `gh` login when present; resumes) and `host.Direct` any other HTTPS address (temp file, size cap).
- **Loaders** (`internal/loader`): a driver registers by id (`smapi`, `bepinex5`, `folder`) and implements `Loader` (`Status`, `Install`, `Contribute`) plus optional capabilities by type assertion. A launch is a `launchplan.Plan` the loader adds to; the profile's launch options, prefix and environment follow, and `game.Starter` runs it through the install's store: Steam through `steam -applaunch` (hands the start to the game and exits), every other store by running the game's executable; a loader that replaces the executable is never relayed.
  - **Pipeline** (`internal/launchsvc/pipeline.go`, tests `pipeline_test.go`, `pipeline_recover_test.go`, `install_lock_test.go`): one install runs one launch at a time (the preparing claim is the lock). Order: loader contributes; enabled packages are laid out in the profile (`SyncPackages`) when the profile holds the loader; the deployer places install-side files (journaled before the first file moves; a loader that redirects the game to the profile, as SMAPI's `--mods-path`, declares none); profile game settings apply and the changed-launch save backup is taken; a `separateSaves` profile's Saves folder is swapped in ([Saves](#saves)); the runtime is prepared (`bepinex5.EnsureWinHTTPOverride` on an existing Proton prefix: persistent, idempotent, not journaled); the store starts the game. When the game exits or the start fails, placed files are purged, the saves swap undone, settings restored. `RecoverDeploys` finishes what a crash or quit left at startup, skipping an install whose game still runs.
- **Installers** (`internal/installer`): an archive's shape picks a driver in `detectionOrder`: `fomod`, `thunderstore-rules` (r2modman's layout rules), `plain` (any archive, last). `Layout` maps archive paths to files under the game's catalog targets; every path is validated to stay inside its target and be storable on Windows.
- **Frameworks** (`internal/framework`): a driver keyed by a framework mod's id; while an enabled mod matches, `Analyze` adds asset conflicts, setting hints, cleanup suggestions and redundancy findings to the profile's problems. Content Patcher is the one driver.
- **Pack formats** (`internal/pack`): `Format` readers turn another manager's list into a `Draft` and write nothing: r2modman and Gale codes (`#r2modman\n` plus base64 of a zip with `export.r2x` and `config/`, fetched by key from Thunderstore's legacy profile endpoint), r2modman profile folders (`mods.yml`), Gale profiles from `data.sqlite3` (`pack.Gale`, read-only; mods JSON names packages as `Namespace-Name-Version`) and Thunderstore modpack packages. `Code.ExportCode` publishes a code to that endpoint (after confirming with the player). `packsvc.ExportModpack` (`mortar profile export --format modpack`) writes a Thunderstore modpack zip: `manifest.json` depending on each enabled Thunderstore package as `Namespace-Name-Version`, a plain 256x256 `icon.png`, a `README.md` naming mods left out and `BepInEx/config` as `config/`; the modpack reader reads it back as the same package set.

### Folder games

`internal/loader/folder` (`folder_test.go`; profile side: `internal/profile/foldergame_test.go`, `syncrules_test.go`): a game with no mod loader names the loader `folder`, a `mods` path role (where the game reads mods, possibly outside the install) and a `mods` target whose root is a profile subfolder (`{profile}/Mods`).

- **Entries:** an added archive lays out below the target as packed and becomes one profile entry per laid-out file, unless it lays out a file whose extension is in the target's `keepWhole` list (a script that only works beside its siblings): then one entry holds every file, keyed by the store item. A per-file entry has key `<store item>#<slash path>` with `Entry.Item` and `Entry.File`. Trap: everything reading the store (backups, listings, keep set, missing-item check, sizes) uses `Entry.StoreKey()`, never the key, so an archive counts once.
- **Replacement:** an install replaces an earlier archive only as its update (a Nexus or CurseForge file whose update names the old file id, `Source.WithReplacing`, or a GitHub release asset of the same repository and asset shape); another file of the same page and a local archive are added beside. An update replaces every entry of the superseded archive together, each keeping its on/off state, and the first new entry records the superseded entries so Roll back restores all.
- **Shared-path files (Tray):** files whose extension a target lists in `extensions`, on a target whose `role` names a shared path (The Sims 4's `tray`), are not part of the profile: placed at install in that folder, never swapped at launch, held by an entry of their own (`Entry.Tray`) recording each file and its SHA-256. A file of the player's own there is never replaced: the install is refused naming it, or an identical file is left and not claimed. Recorded files are released only while no entry of any profile of the game holds them and the file still has the recorded hash; they are placed again when a profile returns from trash or a backup. Update and roll back place new files before releasing old.
- **Catalog fields:** `caches` names rebuildable files below a path role; `requiredSettings` become Problems rows of kind `game-setting`. A mod with no source and no manifest is a `local` entry `folder:<store key>`; nothing updates it. The profile's saves reuse `separateSaves` against the `saves` role.
- **Launch:** the loader plans one file per file below the target with `launchplan.PlanFile.Root` `mods`; the deployer places them under `deploy.View.Roots["mods"]` (`launchsvc.planRoots` via `game.PathFor`) with the same journal and crash recovery as install-side files. Files in that folder the profile does not own are never touched, so the shared folder holds none of a profile's data after the launch. `SyncPackages` records each file it lays out with hash, size and time in `.mortar-packages.json`, never overwrites a copy changed since, and when its package goes away holds the changed copy under `<profile>/changed/` (restored when laid out again); backup and restore carry `changed/`.
- **Settings:** `gameSettingsMode` (`edit` or `warn`, per game, profile-overridable) decides whether Mortar writes the catalog's `requiredSettings` into the profile's own copy of the `options` file before a launch (`launchsvc.swapOptions`) or only reports them. `cacheClearing` (`auto` or `off`) deletes the catalog's `caches` once, on the first launch after the profile's mod set hash (`profile.ModSetHash`, recorded as `cacheSet`) changes, refusing a path outside its role. `newProfileSeparateSaves` makes `Store.Create` start a profile with separate saves. `scripts/selftest.sh regress --game sims4` drives a stand-in Sims 4 install through two profiles and checks the player's files are identical afterwards.

### Deploy methods

`internal/deploy`, `GameInfo.Deploy`. `redirect`: the loader points the game at the profile's folder; nothing is placed (SMAPI's `--mods-path`). `profile`: the profile holds the loader and mods (the r2modman and Gale model): before a launch `SyncPackages` copies each enabled package's files into the profile (a package's config file only seeds it) and removes files of packages no longer enabled; the deployer copies only the loader's install-side files into the install, journals every move first and, when the game exits, removes them and restores what they displaced. Packages are never linked into the install or the store, and nothing else in the game folder is read, moved or taken back. The catalog's `targets` say where each kind of file goes in the profile and how deep it may sit.

- **Install-side files:** the one deployer is `copy-into-install` (`internal/deploy/place.go`). It copies the loader's plan files (BepInEx's Doorstop pair `winhttp.dll` and `doorstop_config.ini`, the config's target made the profile's absolute preloader path so a start that passes no Doorstop flags, such as an Epic Games link, still loads the profile) as real files, never links (the game and its anti-cheat may write to them). A plan path leaving the install is refused.
- **Journal format** (`deploy.go`, `oplog.go`; `crash_test.go` crashes after every step of Apply and Purge): `Apply` hashes each source, records every operation (destination, source, SHA-256, and for an existing destination where the displaced file waits under `<journal>/displaced/<n>`) and persists `deploy.json` in `<data>/journal/<install id>` before the first file moves. That record is never rewritten during the deploy; later steps go to an append-only `deploy.log` (one short line per operation; the folder and rescue lines are flushed before the action they announce, the rest every 128 lines and at the end), and recovery replays the log over the record, ignoring a last line a crash cut short. Each file is copied through a `.mortar-tmp` beside its destination, synced and renamed (`datadir.CopyFile`); a hard-linked destination is never written through. `Apply` refuses with `ErrUnrecovered` while an earlier deploy's journal exists (a second record would overwrite the first's record of the player's own files).
- **Purge invariants** (`deploy_test.go`, `writeback_test.go`): a displaced file goes back over its destination; with nothing displaced a destination is removed only while its hash is the recorded one, so a player's own file Mortar did not place is never deleted. A crash between any two steps leaves the bytes in the profile, the shared folder or both, never neither, and `Recover` finishes the same walk (nothing while the game runs).
- **Write-back rules** (each tested in `writeback_test.go` and `writeback_review_test.go`; the profile owns what a launch changes in files it placed, the shared folder is scratch): a changed file placed from a profile copy into a path role's folder (a folder game's Mods) is copied over the profile's copy before the file is removed, and a file created during play inside a folder an entry owns is adopted (up to 64 MiB a file and 512 MiB a purge, never through a link); the profile's copy (the plan's `Src`) is the only target, never a store item; a file at the role's root, in a folder no entry owns or in the saves folder is never adopted; write-back happens only after the game exits (Windows holds the file open). When the profile's folder is gone bytes are never removed without a copy: a changed file over a displaced one is renamed `<name>.mortar-rescued` (reported in the launch log) before the player's file returns. A created file too large to adopt and any rescue file are recorded beside the journal (`<journal>.shared.json`) and listed by profile health ("Left in the shared folder") until gone.
  - **`changed/<path>` is the one rule** for update, roll back, uninstall and a switched-off package: a changed copy is moved there, never deleted, and comes back when an archive ships it again or the entry is reinstalled.
  - **Transfer:** backups carry changed and adopted files as `changed/<path>`. In a `.mortar` payload they travel exactly as config files do (`Include.ConfigFiles`; a paired LAN send and sync use `share.OwnInclude` and carry them; per-file cap `MaxConfigBytes`, same total and file-count caps; received by `sharesvc` through `profile.WriteChangedFiles`). Copies from another computer are untrusted: the payload reader refuses any path not a clean relative one inside the content folder or `changed/`, the writer checks again, refuses a path that reaches a link, and writes nothing when any path is refused.
- **Files an update drops:** `SyncPackages` records which entry laid each file. A changed file whose entry was replaced by a version that no longer ships it follows `oldFilesOnUpdate` (`keep`, `delete`, or `ask`, moved to `old-files/<entry key>/_files/<path>`); one whose entry was switched off or removed is held under `changed/` whatever the setting, `.mortar-held.json` recording when, and deleted at the next sync once held longer than `trashRetentionDays`. A dropped file nobody changed is removed in every mode. The save backup before an update is skipped when `backupBeforePlay` is `never` for the profile.

### Loader notes

- **SMAPI** (`redirect`): replaces the game's launcher once per install, reads its log from the game's error-log folder and matches it to a profile by the `Mods go here` line; its bundled mods are a store entry in every profile.
- **BepInEx 5** (`profile`): keeps core, plugins, patchers, config and log in the profile, where Doorstop's `--doorstop-target` points (`<profile>/BepInEx/core/BepInEx.Preloader.dll`), and needs only `winhttp.dll` and `doorstop_config.ini` beside the executable (copied in and removed by the deployer); under Proton the `winhttp=n,b` override is written into the prefix. A native Linux build (an install holding `linuxMarker`) gets no files: it starts directly with the pack's `libdoorstop_x64.so` in `LD_PRELOAD` and the Doorstop target in `DOORSTOP_TARGET_ASSEMBLY`, as the pack's own start script would.
- **BepInEx 6 IL2CPP** (catalog `major: 6`): enters through `BepInEx.Unity.IL2CPP.dll` on the .NET runtime it ships in `dotnet/`, named by absolute path in the Doorstop config and CLR flags. Its install also puts the game's Unity base libraries (version from `<game>_Data/globalgamemanagers`, fetched once from `unity.bepinex.dev` into `cache/unity-libs/`) in `BepInEx/unity-libs/`, so the first start needs no network; when the fetch fails they are left to BepInEx.
- Each loader names a hidden companion mod (the SMAPI bridge, the BepInEx bridge) that lets Mortar query the running game.

### SMAPI

- **Pin:** game setting `smapiPin` holds a SMAPI version Mortar installs instead of the latest (and stops offering updates for); an unknown version is refused before the game is asked to close.
- **Patch-day sweep:** when the installed game or SMAPI version differs from the last sweep's (`lastSweepGameVersion`, `lastSweepSMAPIVersion`), every profile is checked for mods smapi.io marks broken for the new versions, and one toast leads to the summary.
- **Install and update:** download the release installer (4.5.2, published 2026-03-22, needs Stardew 1.6.14+; 2 to 4 releases a year) and run it unattended with `--install --no-prompt --game-path "<dir>"`; running it again updates (measured on Linux: exit 0, no prompts, launcher replaced, bundled mods added). Mortar installs SMAPI itself, without asking, when a profile is created, at startup while SMAPI is missing or broken, on first run and before Play when a game update replaced the launcher; only a newer release waits for the user (an update can break mods), as a banner from the GitHub releases client ([GitHub releases](#github-releases)).
  - **Windows:** the installer is `SMAPI <version> installer/internal/windows/SMAPI.Installer.exe`, self-contained (its `runtimeconfig.json` bundles .NET 6.0.36). Mortar extracts the whole zip and runs it from the installer folder, as `install on Windows.bat` does (the batch file refuses a `%TEMP%` path).
  - **Bottles bottle:** a Windows build on a Linux host is recognised by `Stardew Valley.exe` (`buildOS`); the same installer zip runs inside the bottle (`Install.RunInBottle`), and a launch is a direct start wrapped in `bottles-cli run` (`Install.BottleCommand`); with no runtime to run it the install is refused.
- **Versions:** the installed SMAPI version is kept in `settings.json`; otherwise, and for the game version, Mortar reads the first line of `SMAPI-latest.txt` (`SMAPI 4.5.2 with Stardew Valley 1.6.15 build 24356 on Unix ...`, measured).
- **Broken by a game update:** on Linux the installer renames `StardewValley` to `StardewValley-original` and puts its launcher in place, which a game update overwrites. Mortar checks at startup and before launch that `StardewValley-original` exists and `StardewValley` contains `StardewModdingAPI`; Play reinstalls SMAPI first when not. On Windows the launcher survives and an incompatible SMAPI reports itself in its log.
- **Bundled mods:** a profile's `mods/` replaces `Mods/`, so every profile gets SMAPI's Console Commands and Save Backup as a `smapi-<version>` store entry from the installer Mortar downloaded (`internal/<os>/install.dat`, a zip holding `Mods/ConsoleCommands` and `Mods/SaveBackup`, checked in 4.5.2). A SMAPI update replaces that entry in every profile.
- **Profiles folder:** SMAPI takes `--mods-path <path>`, absolute or relative to the game folder (`smapi.md:49`). Its `SMAPI_MODS_PATH` variable works only when SMAPI starts directly (`steam -applaunch` cannot pass environment variables), so Mortar does not use it. Mortar never moves or writes the game folder's own `Mods`; **Import from the game's Mods folder** only reads it.
- **Scanning:** SMAPI recurses into subfolders until it finds a `manifest.json` and skips folders starting with a dot; manifests are parsed leniently. Optional `UpdateCautionMessage` and `DeleteOldVersion` (Stardrop update hints) are read with the same case-insensitive key rules; **Update all** skips cautioned mods until the row is ticked.

#### Components

`components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern, version policy and optional accepted game-version range; its `games` section holds each game's identity, carried unchanged into the manifest. Process names and launch behaviour stay in Go.

- Game implementations read it through `components.Client.Game` (per-game fallback to the bundled manifest). `cmd/components` resolves releases, downloads the named assets and writes the signed `components.json`; the same manifest is embedded at `internal/components/components.json` for offline and first-run fallback.
- **Signature:** Ed25519 with the update key (`build/updater/public.key` is the embedded public half); the detached signature is published beside the manifest. Each signed manifest is its own immutable `components-v2-<serial>` release; `v2` is the manifest schema (released clients read any manifest whose fields they recognise, so a schema change takes a new prefix).
- **Client** (`internal/components`): finds the newest non-draft `components-v2-*` release through the GitHub releases API, fetches its manifest at startup through the daily meta cache, verifies before parsing, rejects a lower serial and falls back to the cached or bundled manifest. Source hosts are limited to `github.com` and `thunderstore.io`.
- **Downloads:** every asset is checked against its manifest SHA-256 before extraction. The bridge is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`, replaced when the manifest version or hash changes. Hidden means as SMAPI's bundled mods ([gui-design.md](gui-design.md#mods-tab)).

#### Mortar SMAPI Bridge

Mortar has no access to SMAPI's stdin, so a small SMAPI mod (`Rethunk-Tech/mortar-smapi-bridge`, `UniqueID` `Rethunk.MortarSmapiBridge`, protocol in its README) accepts console commands on a loopback port.

- **Channel** (`internal/bridge`): the mod writes `mortar-smapi-bridge.json` (`{port, token}`, user-only) in its folder; Mortar reads it from the running profile and sends `<token>\n<command>\n`, so the token never leaves the user's own files. The reply is `ok`, `ok <json>` or `error: <message>`; `Query` (`status`, `plugins`) returns JSON. Commands run on the game's next tick and their output arrives in SMAPI's log.
- **BepInEx companion** (Mortar BepInEx Bridge, `Rethunk.MortarBepInExBridge`): writes `mortar-bepinex-bridge.json` in the profile's `BepInEx/config`, answers `ping`, `status`, `plugins`, hidden like the SMAPI one (`manifest.LoaderManaged`).
- **Running state:** while a game Mortar started runs, `launchsvc` asks `status` every 2 s (`loader.RunningState`). Each enabled package whose DLLs declare plugins gets a loaded or not-loaded badge; plugins are a set, never load order. Trap: BepInEx keeps the newest version of a GUID and, between equal versions, the first file its folder walk meets (`Chainloader.cs`, stable `OrderByDescending` over `Directory.GetFiles` order), which only the bridge's `location` tells, so the loaded plugin is the package whose laid-out file the bridge names.
- **Stream overlay** (UI: [gui-design.md](gui-design.md#settings)): when enabled, Mortar writes the bundled OBS page to `<data>/overlay/index.html`. At launch (and when the bundled bridge is first extracted into the store) it writes the bridge mod's `config.json` (`OverlayEnabled`, `OverlayPort`, `OverlayToken`; 0600, atomic) so a change applies on the next Play; a loader whose bridge keeps settings in the profile (BepInEx, `loader.OverlayArmer`) gets the same keys in `startup/overlay.json`, removed while the overlay is off so the token stays out of other profiles. The page polls `http://127.0.0.1:<port>/state?token=<token>`. Both bridges serve one `/state` shape: `inGame`, `playerName` and the game's own keys; the BepInEx bridge adds `game` (`lethal-company`: `moon`, `crewAlive`, `crewTotal`, `day`, `quota`, `quotaProgress`, `daysLeft`, `credits`; `valheim`: `biome`, `day`, `bossesDefeated`, `bossCount`), which picks the layout; a snapshot with no `game` is Stardew Valley's.

### Launch

| Copy | How Mortar starts it |
| --- | --- |
| Steam | `steam -applaunch <appid> <args>`: Steam passes the arguments after the app ID to the game, keeping overlay, achievements and playtime |
| GOG, Heroic, Minigalaxy | SMAPI directly (the Direct path) |
| Flatpak Steam | `flatpak run com.valvesoftware.Steam -applaunch 413150 --skip-terminal -- --mods-path <dir>`; a timeout while the override is missing uses the filesystem-access hint |

The launch pipeline is [Loaders](#games-and-the-catalog) (`internal/launchsvc/pipeline.go`); the facts below are the ones the code cannot show.

- **Linux Steam:** `steam -applaunch 413150 --skip-terminal -- --mods-path <absolute path to the profile's mods/>`. SMAPI's launcher script reads its own flags only before `--` and forwards only what follows (unix launcher argument loop in Pathoschild/SMAPI), which is why SMAPI's docs say arguments do not work on Linux. `--skip-terminal` makes the script start SMAPI with `--no-terminal`; SMAPI still writes its log (`docs/technical/smapi.md:46`). Measured: without `--` the path is ignored; with it SMAPI loads the profile through a real Steam client; without `--skip-terminal` the launcher opened its console in `xterm`, unreadably small.
- **Windows Steam:** Steam starts `Stardew Valley.exe`, not SMAPI: SMAPI's installer swaps the launcher only on Linux and macOS (`InteractiveInstaller.cs` `if (context.IsUnix)`) and on Windows asks for a launch option to keep achievements.
  - First run shows `"<game>\StardewModdingAPI.exe" %command%` to paste into Stardew's Steam launch options, and **Set it in Steam for me**, which writes `LaunchOptions` in the MostRecent account's `localconfig.vdf` while Steam is closed (Steam rewrites the file on exit) via `internal/steam/localconfig.go`. The write merges (an existing SMAPI `%command%` line is left; a file with no `apps` section is refused until the game has been launched from Steam once). **Remove SMAPI from Steam's launch options** strips that command, leaving other options.
  - Mortar reads `LaunchOptions` and adds `--mods-path <path>` after the app ID. SMAPI finds its flags anywhere on its command line (`Array.LastIndexOf(args, "--mods-path")`, `args.Contains("--no-terminal")`, SMAPI 4.5.2 `Program.cs`) and ignores unknown ones, so the game path Steam substitutes for `%command%` does no harm; an absolute `--mods-path` wins over the game folder (`Path.Combine`).
  - Mortar does not pass `--no-terminal` on Windows: `StardewModdingAPI.exe` is a console program (PE subsystem 3, checked on the 4.5.2 Windows `install.dat`), so Windows gives it a console window whatever the flags. A direct launch hides the window instead (`showSmapiConsole` off); the Console tab follows the log file either way.
  - Without the SMAPI line Steam starts the game, not SMAPI, so Mortar starts `StardewModdingAPI.exe` itself (`game.steamSkipsLoader`, `internal/game/start.go`) at the cost of the Steam overlay.
- **Console input:** a process Mortar starts gets a stdin pipe it holds open until exit (`launch.startCmd`, `internal/launch/launch.go`). SMAPI's console-command loop (`LogManager.RunConsoleInputLoop`) skips empty reads, so on `/dev/null` or `NUL` it spun one core for the whole session (measured: 93% of a core on Linux); on an open pipe it waits. Console tab commands go through the bridge mod, not stdin.
- **SMAPI startup markers:** SMAPI's `Console.ReadKey` throws when stdin is not a console, so the "game crashed last time" prompt (`smapi-internal/StardewModdingAPI.crash.marker`, written on every fatal crash) ended SMAPI before the game opened and the marker survived, failing every later launch (reproduced on Linux, direct launch). The SMAPI loader's `Prelaunch` removes that marker and the update marker before each profile launch; `ErrorLogs/SMAPI-crash.txt` is kept.
- **Extra arguments:** a profile's `launchOptions` are split like shell words and appended after `--mods-path` (on Linux after `--` too); `--mods-path`, `--no-terminal`, `--skip-terminal` are refused since Mortar sets them. `launchPrefix` (Linux only, no shell evaluation) is prepended to a Direct SMAPI command; `launchEnv` (`NAME=value` per line, `[A-Za-z_][A-Za-z0-9_]*=.*`) goes to Direct launches. Steam `-applaunch` receives neither prefix nor environment. Changing any of these never touches `mods/`, so a running game does not block it.
- **Presets** (`internal/profile/launchpreset.go`, `launchpreset_test.go`): the profile's own `launchOptions`/`launchPrefix`/`launchEnv` are its built-in preset `Standard`; `launchPresets` holds up to 20 further named ones (names unique ignoring case, never `Standard`). An unknown preset name refuses the launch before anything starts. A preset's `showConsole` replaces the `showSmapiConsole` override for that launch. `Service.StartPreset` (CLI `launch <game> <profile> --preset NAME`); game-wide **launch preset templates** (`settings.LaunchPresetTemplate`) are copied into a profile through `Store.AddLaunchPreset` and stay independent of the template.
- **Per-profile game settings:** an optional `game-settings.json` beside `profile.json` overrides selected fields in Stardew's `startup_preferences` for that launch. Mortar records the old values, applies the override before starting a profile with mods, and restores each field when the run ends only if the game still has Mortar's value (`internal/launchsvc/gamesettings.go`).
- **Without mods:** `steam -applaunch 413150` with no arguments, or the game's executable when started directly. No profile, no mods lock, refused while the game runs; no `lastPlayed` or run is recorded. On Windows, when Steam's launch options hold the SMAPI `%command%` line Steam still starts SMAPI, so Mortar warns first (and never edits that file); if that check fails Mortar does not start the game.
- **Before Play:** Play gathers missing required dependencies, unresolved non-dismissed non-cosmetic conflicts, pending updates, mods flagged broken or obsolete, a changed game version and the newest save's gap (`savessvc.LastSaveGap`, [gui-design.md](gui-design.md#main-screen)); any found open a dialog with **Play anyway**, **Open Problems**, and **Update and play**. **Don't check before Play** is the `skipPlayCheck` profile override.
  - **Update mods before Play:** when `updateModsBeforePlayDefault` resolves on (opt-in, only when the user presses Play), Play queues every offered, non-pinned, installable update, waits for those items to finish or need a click, then starts the game. A history restore point is recorded first; a failed update rolls those entries back.
  - **Save backup before a changed launch:** before a non-vanilla launch, if the profile's history has an event after the newest stored run (or no previous run), the Saves folder is zipped into `backups/` with kind `update`. A failed zip is logged and does not block Play.
- **Profile shortcuts:** **Add a shortcut that plays this profile** writes `--play=<game>/<profile>`: on Linux `~/.local/share/applications/tech.rethunk.Mortar.play-<game>-<profile>.desktop` (under `$XDG_DATA_HOME`), on Windows a Start menu `.lnk` through `WScript.Shell` COM (`internal/shortcut`).
  - **Add this profile to Steam** appends a non-Steam game to native Steam's `shortcuts.vdf` for the MostRecent account (`internal/steam/shortcuts.go`; quoted exe, launch options `--play=… --steam-session`, appid with the high bit set). An entry for Mortar's exe whose options include the profile's `--play=<game>/<profile>` is that profile's and is updated in place keeping appid and playtime. Refused while Steam runs and when only Flatpak Steam is found (that sandbox cannot start Mortar).
- **Success or failure:** `steam -applaunch` returns at once. A launch counts as started when `SMAPI-latest.txt` (`~/.config/StardewValley/ErrorLogs/`, `%APPDATA%\StardewValley\ErrorLogs\`) is rewritten within 60 s, else failed with a hint. A Steam launch's `steam` process only hands over and exits 0 (ignored; only the log decides); a non-zero `steam` exit fails at once. When Mortar started SMAPI directly and it exits having written no log, the launch fails with its exit code.
- **Running:** a `StardewModdingAPI` process whose `--mods-path` is a profile's folder means that profile is in use; its folder is locked against changes until the process exits. Reaching Running records `lastPlayed` for the game in `settings.json` (profile id, RFC3339 `at`); Launching and Failed do not.
- **Whose log:** the game has one `SMAPI-latest.txt` for every profile, so the Console and Share log show a log only in the profile that wrote it: the session Mortar launched belongs to its profile; the file on disk belongs to the profile whose mods folder matches SMAPI's `Mods go here: <path>` line (SMAPI writes the home folder as `~`, `PathUtilities.AnonymizePathForDisplay`); a log without that line (a launch outside Mortar) belongs to none. A BepInEx log is inside the profile and necessarily that profile's.
- **Runs:** when a launch Mortar started ends or fails, a Summary of that run's log is stored under `runs/` ([Storage](#storage)); `internal/launch/summary.go` lists the fields. A loader with a Unity player log (`WithPlayerLog`) marks the run `crashed` when that log, written since the run began, holds `Crash!!!` or `Fatal error` and the loader reported no crash itself. The Mods list badges each user mod that logged errors or warnings in the newest stored run.
- **Likely cause:** `launchsvc.CrashHint(game, profile)` (`crashhint.go`, `stackhint.go`, `dumphint.go`, with tests of the same names) explains the latest `crashed` run; the first hit wins, in this order: the run's recorded cause; the loader's log analyzers (first finding whose plugin is an enabled installed mod); for loaders with .NET stacks (`loader.WithStackBlame`, `smapi.StackBlame`, `stack_test.go`) the first mod frame nearest the throw of the last exception block that runs through a mod, skipping runtime and game namespaces, a stack of only Harmony patch frames blaming the Harmony id shown beside it, and two equal matches blaming neither; a crash dump (`internal/crashdump`: Unity `Crash_*` folders and WER dumps newer than the run start on Windows-code games, a pure-Go minidump parse for the faulting module, `coredumpctl` on Linux), blaming a mod only when the faulting module is its `EntryDll` or a same-named file within three folders of its folder (the game's executable, `UnityPlayer` and Mono name that part of the game and no mod); else the first finding's message with no mod. The profile page shows a card with **Disable and retry** and **Bisect from here**.
- **Bisect** (**Find the broken mod**, offered when the crash names no mods; `internal/bisect`, `launchsvc.RunForBisect`): runs on a scratch profile (`profile.ScratchCopy`: a `.scratch-<id>` folder no listing shows, removed when the check ends and, after a crash, at the next start), halving enabled mods (keeping required dependencies). A step fails only when SMAPI logs an alert or the run ends crashed; plain errors such as a skipped mod do not count, or the bisect would blame whichever mod logs one. A step passes when the bridge writes a title-screen report under `<profile>/startup/`, or after 20 s at Running when the profile has no bridge folder; `bisectRunTimeout` ends a hung step.
- Trap: launching through Steam makes Steam Cloud download the user's saves, and SMAPI's Save Backup mod zips them into `save-backups/` in the game folder.

### Startup timings

- **What:** the bridge measures each mod's share of startup, from its own Entry to the title screen, and writes `<profile>/startup/<process start UTC>.json` (last 10 kept; schema in the bridge README). Times are exclusive: an asset edit triggered from another mod's update tick counts for the editor only. The report's `replaces` lists, per Harmony ID (a mod's UniqueID by convention), the game methods it can replace outright (transpilers and `bool` prefixes); Problems adds them to each C# mod's footprint ([Same job](#same-job)).
- **Load early:** before each launch Mortar adds the bridge's UniqueID to `ModsToLoadEarly` in `<profile>/mods/SMAPI-config.json`, keeping other keys (a file that is not plain JSON is left alone), so every other mod's Entry runs after it.
- **Measured launch:** **Measure next launch** writes `<profile>/startup/.measure-next-launch`; the next launch removes it and writes `StartupProfile: true` into the bridge's `config.json`, so the bridge also times every other mod's Entry (from SMAPI's per-mod `SetApi` call, never by patching a mod's method) and skips the title intro animation. Timed: every SMAPI event handler (delegates swapped in place on SMAPI's event manager, restored at the title screen), every asset edit and load by mod and by content pack, and Content Patcher's per-pack work. Measured on the main profile (193 mods, 417 packs): 44 s of 46 s between the bridge's Entry and the title screen attributed; Content Patcher's first update tick 26 s, Fashion Sense's GameLaunched 2.9 s.
- **Shown in:** Performance › Startup ([gui-design.md](gui-design.md#performance-tab)), the Mods list's Startup column, and Since last run, which names each mod updated or added since the previous report that made startup at least 1 s slower (smaller is run-to-run noise).
- **Sampled launch:** with **Measure next launch** set, Mortar starts a diagnostics EventPipe session as soon as the game process appears, requests rundown when the title-screen report appears and writes `report-id.samples.json` under `startup`; each sample is charged to the innermost frame in an enabled mod assembly, unmapped samples are game and SMAPI time (`sampleMs`, `sampledOtherMs`). Sampling failures do not fail the launch. A test or bisect launch waits for the sampler to stop its session before stopping the game (the method rundown needs the live process). Findings on the main profile (53.5 s to the title): named mods held 81% of sampled time and agreed with the bridge within a second for Content Patcher (25.8 s), Fashion Sense and JsonAssets; the sampler alone showed Better Artisan Good Icons at 9.0 s, spent in its patches on game code.
- **BepInEx:** only a measured launch is timed. The launch turns `.measure-next-launch` into `<profile>/startup/.measure-launch`, holding the catalog game's `titleScene` (Lethal Company `MainMenu`, Valheim `start`). The bridge's preloader patcher (`BepInEx/patchers/<package>/MortarBepInExBridge.Patcher.dll`) consumes it and adds a log listener before the chainloader runs, so it sees every plugin's `Loading [Name Version]` line; `LogOutput.log` has no timestamps and is flushed on a timer, so timing cannot come from it. A plugin's `entryMs` is the gap to the chainloader's next plugin line (constructor and Awake); later work lands in the first-scene-to-title phase. Phases map onto the same fields: `bridgeEntry` preloader, `entryDone` "Chainloader started", `gameLaunched` "Chainloader startup complete", `titleMenu` first scene loaded, `titleScreen` the title scene. Unity's Mono has no diagnostics port: no sampling, no Sampled column.
- **In-game frame timing:** the same measured BepInEx launch sets `MORTAR_MEASURED_LAUNCH=1`, and the bridge plugin keeps frame stats and, from the first `perf start`, wraps every plugin's Harmony patch methods and its MonoBehaviours' Update, LateUpdate and FixedUpdate with timers. Both companions answer `perf start` and `perf` (the summary, rebuilt once a second) with `{measured, seconds, frames, fps, frameMs{avg,p50,p95,p99,max}, monoUsedBytes, monoHeapBytes, gcCollections, baseline{frameMs, modsMs, withoutModsMs}, plugins[{guid, msPerFrame, p95Ms, peakMs, share, callsPerFrame}]}` (BepInEx also `patchOwners`: Harmony ID to patched game methods). The SMAPI bridge wraps each mod's handlers of the per-frame events only from `perf start` for at most ten minutes; SMAPI's own performance monitor has no 95th percentile or frame share, so it is not the source. `p95Ms` is a histogram (about 10% resolution), `share` is the average over the average frame, and `baseline.withoutModsMs` is the average frame less the mods' timed code (not a launch with no mods). `launchsvc.MeasureInGame` (`perf_bridge.go`) saves the rows, named by package (a BepInEx plugin by the GUID its DLLs declare, a SMAPI mod by UniqueID), as a performance report.

### Antivirus scan

- **Where:** `Store.install` (`internal/store/store.go`) calls `checkExtracted` (`internal/store/scan.go`, tests `scan_test.go`) on the extracted folder after junk is stripped and before the rename that makes it an item, so every path into the store passes it (archive, hashed dir, LAN receives, backups, profile imports). Loader bundles are Mortar's own downloads and are skipped.
- **Scanners** (`internal/avscan`, `Scan(ctx, dir) (Detection, bool, error)`): Windows AMSI through `amsi.dll` (`AmsiScanBuffer` per 32 MiB of each file; a result of 32768 or more is malware; AMSI names no threat, so the row says "malware reported by the Windows antivirus"); clamd over a unix socket (`zINSTREAM`, 64 KiB chunks; socket: the setting, else `/run/clamav/clamd.ctl`, `/var/run/clamav/clamd.ctl`, `/run/clamd.scan/clamd.sock`, `/var/run/clamd.scan/clamd.sock`, `/tmp/clamd.socket`); a custom command (no shell; `{path}` replaced by the folder; exit 0 clean, any other code a detection named by the first stdout line); or off.
- **Settings** (`antivirus`, `antivirusSocket`, `antivirusCommand`): `automatic` (AMSI on Windows, clamd elsewhere), `clamd`, `command`, `off`. Socket and command are not portable fields.
- **Detection:** the install fails with `store.DetectedError` under `usererr.Malware` (`malware` on the wire) and the extracted files are deleted. The queue item fails with `errorKind` `malware`; the bound call's error carries the detection as typed fields (`usererr.Marshal` adds `detail` for any `usererr.Detailer`: `game`, `key`, `name`, `file`, `scanner`) and the frontend reads them with `detectionOf` (`frontend/src/toasts/avOverride.ts`), so no error-text parsing. **Install anyway** confirms, calls `profile.Service.AllowUnscanned` (the next install of that key skips the scan once) and records a `ChangeUnscanned` history event; CLI `mortar install ... --allow-unscanned`.
- **Real-time protection:** a file Windows blocks or deletes while Mortar writes or reads it reaches the same place: `store.RealTimeBlock` (`realtime.go`) turns `ERROR_VIRUS_INFECTED`/`ERROR_VIRUS_DELETED` (225, 226), or a file vanished from a staging folder, into a `DetectedError` with `Removed` set; the file is gone, so there is no Install anyway.
- **Errors:** a scan that fails or times out (2 minutes) is not a detection: the mod installs, the log keeps the error and an `avscan:failed` event shows "The antivirus scan could not finish, so a mod was installed unscanned". "No scanner" is silent. `mortar antivirus status` (`avscan.StatusOf`) prints the mode, scanner kind, product and whether a scan can start now.
- **Acceptance:** `scripts/av-smoke.ps1` in the Windows VM (installed, running Mortar; `-ZipDir` default `C:\avsmoke` needs a Defender exclusion) builds a zip at run time from parts (Microsoft's AMSI test sample for `amsi`, EICAR for clamd; the repo never holds either string), installs it into a throwaway profile through the CLI, expects the `malware` refusal, repeats with `--allow-unscanned`, checks the profile history and writes PASS/FAIL and `failures: N` to `%LOCALAPPDATA%\Temp\mortar-av-smoke.txt`.

### Saves

Saves live in one folder, `%APPDATA%\StardewValley\Saves` or `~/.config/StardewValley/Saves`, which Steam Cloud syncs, so Mortar never moves it; profiles share saves unless one sets `separateSaves`.

- **Per-profile saves** (`internal/savesiso`, tests `savesiso_test.go`, `fileswap_test.go`): a profile with `separateSaves` plays on `<profile>/saves` for the length of a launch with mods (a vanilla launch plays on the shared folder). `Apply` persists `Manifest{Journal, Saves, Profile, Held, Copied, Live}` as `saves.json` in `<data>/journal/<install id>-saves` before the shared folder moves, renames the shared folder to `<Saves>.mortar-shared` (a rename, never a copy), then points the save path at the profile's folder with a symlink; where a symlink is refused it makes a working copy and sets `Live` once complete. `Purge` undoes it, checking the disk at every step so it can run again after a crash; an incomplete copy is dropped, never written back. `Apply` refuses with `ErrUnrecovered` while a record of an earlier swap exists. The swap is undone with the deploy when the game exits or the start fails; `RecoverDeploys` finishes one a crash left (`savesiso.Recover`).
- The Saves tab lists every save with the mods it has used that the profile lacks, read from the save itself, and which profile last played it (`<game>/last-played.json`) ([gui-design.md](gui-design.md#main-screen)). Play warns from the newest save ([Launch](#launch)).
- **Where mods leave traces:** SMAPI writes no mod list into a save, but mods leave keys prefixed with their `UniqueID`: SMAPI's save data `smapi/mod-data/<uniqueid>/<key>` (lowercased whole) and `modData` keys such as `Sonozuki.MoreGrass/GrassOffsetX0`. Mortar scans the save's `key`/`string` XML entries and, ignoring case, takes for each key the longest prefix ending at a `/`, `_` or `.` boundary that is a `UniqueID` in the mod dataset's index. Splitting at the first `_` would be wrong: 1,413 IDs contain `_` and for 81 the part before it is another mod's ID; 1,081 have no dot.
- **Cost:** measured on a real save, 65 MB, 330,748 keys, 32 mods in 0.43 s; cached by the save file's mtime. The same streaming pass reads `SaveGameInfo` for farmer, farm name, in-game date, `millisecondsPlayed`, `money`, and the farm layout `whichFarm`: 0 Standard, 1 Riverland, 2 Forest, 3 Hill-top, 4 Wilderness, 5 Four Corners, 6 Beach, 7 Meadowlands; -1 when the tag is missing.
- **Limits:** mods that keep no per-save data leave no trace and keys outlive a mod removed on purpose, so the warning says "this save has used", and each mod can be dismissed per save.
- **Backups** (`internal/savessvc`; naming, kinds and rotation: [Storage](#storage)): the Saves tab lists `backups/` zips newest first. Restore first zips the current Saves folder (kind `restore`), extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one; it refuses a zip path that would leave the extract folder, caps each file at 512 MiB, and is refused while the game is launching or running. **Back up now** (`manual`) is kept until unkept; `DeleteBackup` refuses a pinned zip.
  - **Scheduled** (`savessvc.RunScheduledBackups`, `scheduled.go`, `scheduled_test.go`): every 10 minutes it checks whether `saveBackupHours` has passed since the last pass (measured from the newest `scheduled` zip after a restart); a due pass waits while the game is launching or running (including one Mortar did not start), zips each save folder changed since its own newest scheduled zip and emits `saves:scheduled` (`at`, `saved`, `unchanged`, `failed`, `error`). Backup stamps more than 5 minutes ahead of the clock are ignored; a pass with failures retries after 30 minutes at most.
- **Per-save gap:** `savessvc.SaveGap(game, profile, save)` compares the mods the save was last played with (`last-played.json`) against the profile: `missing`, `disabled`, `versionOlder` (enabled below the recorded version) (`gap_test.go`). A save with no record has no gap. Each lacking mod is located as Problems locates a missing dependency (`problems.Locate`): a Nexus page or GitHub repository gets Add to this profile, any other page an Open link.
- **Content Patcher config suggestions** (Problems; `internal/framework/contentpatcher/settings.go`, `settings_recolour.go`, tests `settings_test.go`, `settings_recolour_test.go`, `variant_suggestions_test.go`): a change or dynamic token whose `When` pairs a `ConfigSchema` field with `HasMod` of another enabled mod is a compatibility patch. An on/off field whose current value (`config.json`, else schema `Default`) runs none of the pack's compatibility patches is suggested with the values that would; fields that list NPCs are never suggested. A variant picker (palette, recolour) is recognised from the pack's own mapping (a dynamic token yielding a field value only when a mod is installed; two or more such values make a picker); `auto`, `automatic`, `detect`, `off`, `none` and fields mapped by `HasMod` are left to the pack. **Set to** writes only that field into `config.json` and remembers the UniqueID, field and value so the reverse suggestion stays hidden until the field's current value changes.

### Mod data

- **Mod dataset:** SMAPI's `Pathoschild/StardewModDataset` (MIT or CC-BY-SA 4.0, published with explicit permission from the sites it lists, refreshed near the end of each month, 0.x with no version tags) records each Nexus mod page's current files with the SMAPI manifests inside (`Downloads[].Mods[]`, `SizeInBytes`), not every file: Content Patcher has 2 there against 170 on Nexus. Fetched per page when needed from `https://raw.githubusercontent.com/Pathoschild/StardewModDataset/main/dataset/data/Nexus/<mod id / 1000>/<mod id>.json`; the `UniqueID` index (`dataset/indexes/pages by mod ID.json`, 1.5 MB, 28,634 IDs) monthly. Parsing is lenient; a file it lacks is checked after download.
- **Update checks:** `POST https://smapi.io/api/v4.0.0/mods` with each mod's ID, `UpdateKeys`, installed version, plus `apiVersion`, `gameVersion`, `platform`, returns `suggestedUpdate`, taken as given; `compatibilityStatus` and `brokeIn` come only with `includeExtendedMetadata: true`. Unofficial versions (`metadata.unofficialUpdate`/`unofficial`/`unofficialForSmapi`) show as **Unofficial update available**; **Update all** never installs them. The API is public, unauthenticated and officially unreleased: answers are cached an hour in one cache shared by every profile, misses go in batches of 100, and after a failed ask Mortar serves stale or unknown answers for five minutes before asking again; failures never block.
- **Dependencies:** `Dependencies[]` (`UniqueID`, `MinimumVersion`, `IsRequired` defaulting to true) plus `ContentPackFor` as a required dependency on its framework mod, all by `UniqueID`. For a missing one Mortar prefers the Nexus page named in its own `UpdateKeys`, else the page whose files hold it at the highest version (3,793 IDs appear on several pages), and takes the newest `MAIN` file satisfying `MinimumVersion`. One found only on CurseForge is listed with its page link; one on no site Mortar has a driver for (e.g. `ModDrop:N`) is listed by name with no link. After an archive install and after a queue item finishes, any required dependency still missing is offered in a dialog whose Add them queues it by the Problems resolver; optional dependencies stay on the Problems bar.
- **Support:** Share log uploads the shown profile's `SMAPI-latest.txt` as on disk, or a stored run's log (`mortar logs share <game> <profile> [run]`), at most `launch.MaxLines` x 256 bytes, to smapi.io/log via `internal/logshare`: `POST https://smapi.io/log`, form-encoded `input=<log text>`, no auth. Trap: the server answers a success with a redirect to `/log/<id>` (the link) and a failed or empty upload with HTTP 200 and its page, so only a redirect counts as success (SMAPI's log parser in Pathoschild/SMAPI). A SMAPI log holds local paths including the user's name and anyone with the link can read it, so Mortar shows the log and asks first. Only a loader with the `loader.LogShare` capability (SMAPI) offers Share log, since smapi.io's parser reads no other loader's log (`support.CanShare` refuses the upload in the app and CLI); other loaders offer Save log and Copy log.
  - **Save diagnostics** writes a zip through the native save dialog (`mortar-diagnostics-<date>.zip`): `build.json`, `settings.json` with `nexusName`/`nexusUserId` cleared and every field whose name says token, secret, key or password removed, `profiles.json` (ids, names, entry counts, mod names, versions, sources; no notes), `queue.json` without `nxm://` keys, `doctor.txt` (as `mortar doctor`), `runs.json` (3 newest, no log text), the last 2,000 lines of `mortar.log`, `mortar.prev.log`, `crash.log`, the open profile's SMAPI log when it owns it, and `manifest.txt` saying what is in and stripped. The home folder is written `~` in every text file and the keyring is not read. **Attach diagnostics** saves the same zip then opens the GitHub issue (a URL cannot carry a file); Report a Mortar bug opens a prefilled issue with no log.
- **Console links:** in visible log rows, exact installed mod names and `UniqueID`s link to the mod's panel, and paths under the profile's `mods/` or the game folder open their containing folder (`OpenConsolePath`, which resolves symlinks and refuses any other path).

### Problems

Problems warn and never block. The checks are in `internal/problems` (one file per family, each with a `_test.go`); each records per-family timings on the cached `Result` and logs `problems: <profile> <family> <duration> (<count> packs)`. Rules that are not obvious from it:

- **Minimum game version:** a mod declaring one newer than the install's (SMAPI `MinimumGameVersion`, Vintage Story `modinfo.json` `game` dependency) is compared against the loader's game version or, where it knows none, the version the game's last run logged (Vintage Story's `Game Version: v…` line).
- **Broken, obsolete, abandoned:** from SMAPI's API for the game version, with `compatibilitySummary` when supplied and a one-click replacement when the summary names a Nexus or GitHub target Mortar can install or a `UniqueID` the dataset resolves. **Superseded** (the summary names a replacement that is enabled too) drops that mod's Broken and Compatibility rows. Abandoned is info-level and dismissible per profile; compatibility-list rows are informational and not counted.
- **Source flags** (`internal/problems/source_flags.go`): `Broken` rows with `Source` naming the site: Nexus pages whose cached status is not `published` (read from the page cache, never fetched) and, through `source.StandingChecker`, Modrinth `archived` (`GET /projects?ids=`, 100 per request), CurseForge Inactive (7), Abandoned (8), Deleted (9) or `isAvailable: false` (`POST /mods`, 500 per request), GitHub `archived: true` (`GET /repos/<owner>/<repo>`, at most 20 per pass, stopping on a rate limit). Each site's answer is cached a day under `cache/standing-<site>-<hash>.json` (`meta.StandingPrefix`, expired by Clean up). Thunderstore deprecations are `DeprecatedPackage` rows with **Replace with** the package the deprecated one's own summary names.
- **Known broken** (`known_broken.go`): the game's `knownBroken` list, matched by mod id or Thunderstore "Namespace-Name" and version range.
- **Redundant:** **shadowed** (a content pack every change of which later packs overwrite) and **sameJob** ([Same job](#same-job)); a mod is listed once and each same-job group is one row and one count.
- **Runs:** enabled mods that logged errors in the newest stored run (warning when it crashed, info otherwise; cleared by a later clean run). `LoadFailure`: plugins the loader's log says failed to load. `PluginClash` (`pluginclash.go`): a `[BepInPlugin]` GUID declared by more than one enabled package (read from compiled plugins through `internal/dotnet`; BepInEx loads only one), with **Keep newer**.
- **Nexus-listed requirements** come from batched page data (`nexussvc.Prime`, asked without a key when signed out; a cold 811-mod profile costs 13 GraphQL requests). The game's loader is never reported; any other outside download is a note with only Dismiss. Trap: Nexus lists a page-wide outside requirement for every file of the page, sub-packs included, so it is only Optional for a file whose own manifest declares dependencies and names none like it.
- **Cleanup** (listed, not counted; `cleanup.go`; **Remove** drops the framework, [gui-design.md](gui-design.md#problems-tab)): frameworks no enabled mod or content pack needs but a switched-off mod still names; conservatively detected unused Content Patcher tilesheet packs (packs that only `Load` new sheets; one that edits an existing sheet is a retexture and never a candidate); enabled mods made for a recolour the profile does not have enabled.

#### Content Patcher conflicts

Rules: `internal/framework/contentpatcher` (`contentpatcher.go` for what counts, `winner.go` for the winner, `conflict_evidence.go`, `footprint.go`, `shadowed.go`; tests `contentpatcher_test.go`, `winner_test.go`, `conflict_evidence_test.go`, `contentpatcher_regression_test.go`). The invariants:

- **What counts:** two or more enabled packs that `Load` the same target (warning: only one wins; a Load without `Priority` is `Exclusive`), or that `EditImage`/`EditMap` the same target or `EditData` the same entry or field (info, dismissible per profile via `settings.json` `dismissed`). `EditData` that only shares a target is not reported. Overlap is never reported between packs built to work together (one entry, or one names the other as a manifest dependency or in a `HasMod` condition).
- **Only edits that can both apply count:** a `HasMod` condition counts only when it holds for the profile's enabled mods; a change whose config conditions do not match the pack's current settings (`config.json`, else schema `Default`) is not counted; edits needing different spouses, or disjoint literal `LocationName`, `LocationContext`, `Season`, `Weather`, `DayOfWeek` or `FarmType` values, never apply together. Image edits conflict only where an opaque 16x16 source cell lands; the same literal value never clashes; JSON equality is by parsed value, so formatting creates no conflict.
- **Cosmetic or harmless:** a conflict whose every overlap is harmless (both image edits, both text edits, a literal `LocationName`/`LocationContext`/`Weather` gate, a one- or two-tile area at a tokenized position) shows under **Cosmetic or harmless** and is never counted.
- **Evidence** is per pack (name, source file, patch index, Action, Target, areas, short When summary, Priority). `Problems` leaves it out (it was 87% of the result: 291 KB of conflicts JSON became 25 KB on the main profile); `ConflictEvidence` returns one conflict's when **Why?** is expanded, `ConflictImageCrop` the image crop.
- **Fixes:** a conflict lists the settings that remove one pack from it: per pack the narrowest on/off field every clashing edit needs, offered as **Set the field to its other value**; a field that would leave the pack nothing active, or that gates a fifth or more of its patches without being named for the target, is never offered. Weighing the master-switch rule by the assets a field reaches (instead of its share of patches) offered no new fix on the main profile and withheld fixes from small packs, so the one-fifth patch share stays. A losing low-priority load gated by a user-changed config value produces a setting hint recommending the pack default.
- **Conflict winner:** "Make <mod> win" records the loser's UniqueID in the winner entry's `loadAfter` and adds it to the winner's installed `manifest.json` as an optional dependency, so SMAPI loads the winner later; the profile's `manifest.json` is its own copy, so the store is untouched, and the dependency is rewritten after an update. Load-against-Load conflicts still need one mod disabled.
- **Reading packs:** targets come from `content.json` and recursive `Action: Include` `FromFile` paths that stay inside the pack folder (JSON comments and trailing commas tolerated; targets containing `{{...}}` skipped). Cached by each `content.json` mtime.

#### Same job

Redundant lists enabled C# mods that change the same game members. A mod's footprint is the `StardewValley` properties and fields its `EntryDll` assigns, read from the compiled IL (`internal/dotnet`, `internal/framework/contentpatcher/footprint.go`, `internal/problems/samejob.go`), plus its Harmony-replaced methods from the startup report; cached by file size and mtime in `cache/problems-assemblies.json`. Input-only members (`mouseClickPolling`, `lastClick`, `FacingDirection`) are dropped from every footprint.

- Scoring: members weighted ln(N/df) over the enabled C# mods with a footprint. A pair is flagged when the shared weight reaches 0.45 of the larger mod's total and some shared member is written by 12 mods at most (under 20 such mods: one footprint inside the other, every shared member written by three mods at most), unless one depends on the other, they share an author or download, or another enabled mod depends on either.
- A smaller mod is also listed on its own row as covered by a larger one when the larger changes 0.8 of its footprint by weight, the smaller footprint weighs at least 10, and every shared member is written by 12 mods at most. Without those guards large mods cover one-member mods incidentally (118 such pairs on the main profile, 2 left with them).
- Measured on the 782-mod main profile: 177 code mods' assemblies read in 330 ms cold, 0.6 to 1.5 ms warm, 7 ms to score.

#### Asset map

Every asset an enabled mod changes (`internal/framework/contentpatcher/assetmap.go`, `internal/problems/assetmap.go`), with each mod's Action and Priority and the winner. Mods are ranked in SMAPI load order (`internal/loadorder`), not profile order.

- Edits apply by priority, then load order, then patch order ([Content Patcher's EditData docs](https://github.com/Pathoschild/StardewMods/blob/develop/ContentPatcher/docs/author-guide/action-editdata.md), Priority). Trap: for Loads the last loaded wins on a tie although the Load docs say "first" (`PatchManager.ApplyPatchesToAsset` replaces its pick with every later candidate that is not strictly lower); two Exclusive loads apply neither.
- A losing mod offers **Make win** only when it ties the winner's priority and no other mod in the group already loads after it through its dependencies; otherwise the only fix is **Disable**.
- The index is cached per profile under the same fingerprint as the problems result (819-mod profile: 91,754 assets, 1,002 changed by more than one mod; ~1 s CPU on first open once the content-pack cache is filled, 8 s with it cold, then 40-120 ms per search or page). Json Assets and Dynamic Game Assets item IDs are not indexed (Dynamic Game Assets is retired in Stardew 1.6).

#### Measured costs of problem scans

- Reusing each patch's shape index and a pack's reachable dynamic tokens within a check: conflicts, settings, redundant and cleanup take 0.56 s per check against 0.92 s, identical output (same sha256). CPU time, main profile.
- The tilesheet map-file scan is saved in `cache/problems-map-scans.json` (gzip; uninstalled folders pruned after each check): first cleanup scan after launch 0.65 s instead of 0.82 s; loading the 2,927 saved scans 29 ms; the file is 330 KB.
- Problems reads the newest run's id from the run index rather than its 0.65-1 MB log (5.1 to 4.2 ms per call).
- The one-time zip-name repair walks the store and profiles (0.16 s CPU, 105k files) once: `names-repaired` in the data folder marks a clean pass. Every launch points a mod record whose folder is gone at the one folder differing only by U+FFFD standing for real characters, so switching that mod off keeps working.
- **Measured, not worth optimising** (main profile: 819 mods, 48,484 files under `mods/`): a full store walk 82 ms (180 ms with a stat per file) over 53,758 files; a profile walk 72 ms; the problem-scan cache 2.5 MB gzip (31 MB raw), rewrite after one pack changes ~0.55 s CPU, load 0.47 s per process; a drift scan of 48,484 files ~220 ms, reused within 5 s; `Installed()` over 819 manifests 18 ms. Caps: queue history 1,000 items (299 KB), `nexus-seen` 2,000, runs by the `runsKept` setting. JSON Lines for the append-only logs would not help: reading, parsing and rewriting `history.json` (51 KB) costs 0.5 ms CPU per event and `download-history.json` 5.3 ms per finished download, and events are edited in place and both files are trimmed to their cap. Opening a 418-mod profile in the self-test build: mod cards 171 ms after the click, size footer 1.1 s, no main-thread task over 50 ms; cold start first request 112-128 ms after process start, ~120 binding calls in the first 5 s (~2 ms each) and none at idle.

#### Generic Mod Config Menu

Menus a mod registers with GMCM or GMCM Options come from mortar-smapi-bridge, which runs inside the game: it writes each menu to `<profile>/gmcm/<UniqueID>.json` (index `_index.json`). Edits made through `mortar mods menu` wait in `<profile>/gmcm-pending/<UniqueID>.json` until the next launch, when the bridge applies them through the setters registered with GMCM, then the mod's save callback, and writes `<UniqueID>.result.json` (applied or skipped). The bridge finds the profile by walking up from its folder to the first holding `profile.json`.

The config editor lists the menu as an **In-game menu** file with typed rows; widgets the bridge cannot set (colour, image, custom drawing) are read-only. A change goes through `Store.SetGmcmOption` (`internal/profile/gmcm.go`), which checks it against the capture, writes or drops the option's pending edit and records a history event; the pending files are part of the config capture history keeps, so Undo puts them back.

#### Other per-entry settings

- **Update channel:** an entry's `updateChannel` is empty (main files only), `optional` (also newer OPTIONAL files on the same Nexus page) or `beta` (also prerelease versions); it filters offers where pins and skipped versions do.
- **Config presets:** a mod's `config.json` can be saved by name under `<data>/config-presets/<game>/<local id>/<name>.json` and applied to any profile's copy as one history event.
- **Groups and health:** a profile's `groups` enable or disable together in one history event; after each problem check the counts are appended to `health.json` beside `profile.json` (newest 200 points).

## Nexus Mods

Sources: the API acceptable-use policy (help.nexusmods.com article 114), the SSO demo `Nexus-Mods/sso-integration-demo`, the `Nexus-Mods/node-nexus-api` client, and Vortex's (`Nexus-Mods/Vortex`) `NXMUrl.ts`. Client `internal/nexus` (REST v1, GraphQL v2), service `internal/nexussvc`; endpoint shapes and caching are in their tests, not restated.

- **Sign-in:** Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours. `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Browser sign-in (off until Nexus issues a slug or client id):** the build flags pick the flow: `-X github.com/Rethunk-Tech/mortar/internal/nexussso.ClientID=<id>` selects OAuth PKCE (wins over a slug), only `-X .../internal/nexussso.Slug=<slug>` selects legacy SSO, neither hides sign-in. Registration facts: [nexus-application.md](nexus-application.md).
  - **Legacy SSO** (`internal/nexussso/sso.go`): `wss://sso.nexusmods.com`, send `{id, token, protocol: 2}`, open `https://www.nexusmods.com/sso?id=<uuid>&application=<slug>`, read the API key off the socket.
  - **OAuth2 PKCE:** S256, scopes `public openid profile`, one fixed loopback redirect `http://127.0.0.1:51762/oauth/callback` (`nexussso.RedirectURI`; Nexus registers a non-dynamic callback); a taken port fails the sign-in and never tries another. Tokens live in the keyring as `nexus-oauth`. With a client id built in, every Nexus call carries the access token as `Authorization: Bearer` (`nexussvc.Authed`), a pasted or legacy-SSO key is refused and the stored key is never read.
  - The personal API key path stays compiled in until OAuth ships, isolated in `nexussvc/apikey.go`, `nexus/auth.go` and the key box (each marked `remove with the API-key path once OAuth ships`).
- **Browse:** search uses the public v2 GraphQL endpoint (`POST https://api.nexusmods.com/v2/graphql`), which needs no key. Trap: a category list is an AND in Nexus's filter, so included categories become one OR branch each, every branch also excluding the excluded ones; category names come from the game's category list, which Nexus serves only to a signed-in account. GitHub search is `search/repositories` with the game's topic (`topic:stardew-valley-mod`; Lethal Company `lethal-company-mod`); without a topic it does not search.
- **Downloads need the user ([AGENTS.md](../AGENTS.md)):** update checks (including the background check every four hours, which only notifies) are allowed, but a Nexus file is never downloaded or installed without a user action (Play with update before Play on, an install, an import, a restore, a Retry, the CLI), and a queue restored from a previous session is held paused at startup when it holds a Nexus file. A Nexus collection link previews and imports like a share link.
- **Update path:** a Nexus mod's update comes from SMAPI's API through the mod's `UpdateKeys` (`Nexus:<id>`), asked in batches ([Update checks](#mod-data)), and the Nexus file lists then decide the file. Trap: Mortar never searches Nexus once per installed mod for updates (`problems` skips `nexus` and `github` sources in its per-source update search): that would spend hundreds of the hourly quota to repeat SMAPI's answer. Page data for many mods is one GraphQL `legacyModsByDomain` request per 50 mods (`nexus.Client.ModsByDomain`; Nexus caps a query's complexity at 10,000 and a mod with its requirements costs ~160), cached by `nexussvc.PrimeDetails`.
- **Manual downloads:** per-game `offerNewDownloads` offers new archives landing in the user Downloads folder or Mortar's download folder, one toast per batch; nothing installs on its own (`internal/dlwatch`, `archivesvc.NewDownloads` with the `lastDownloadsSeen` mark, `internal/folderwatch`). A Nexus file name `<name>-<modId>-<version>-<timestamp>.<ext>` supplies the mod id, otherwise `dlwatch.Identify` peeks `manifest.json` in a zip.
- **Rate limits** (measured on a free account): `x-rl-daily-limit: 20000`, `x-rl-hourly-limit: 2000`, with `-remaining` and `-reset` headers; the client reads them on every response and pauses before running out. Settings › Nexus account shows the last counts with no call of its own.
- **Mod page details** (`nexussvc.Details`): the page, `files.json`, `changelogs.json`, requirements and the category name (`GET /v1/games/stardewvalley.json`, cached 30 days) live in `<datadir>/cache/nexus/details-v4-stardewvalley-<mod id>.json`, never in `profile.json`; signed out, rate-limited or offline, the cached copy is served however old. `available` false marks **Hidden on Nexus**, `status` other than `published` **Removed from Nexus**; those pages are not offered as updates. Changelog notes containing `breaking`, `incompatible`, `requires`, `now needs`, `new save`, `start a new`, `not save compatible` or `remove before updating` mark the update row with a warning ([gui-design.md](gui-design.md#download-queue)). `changelogs.json` maps each version, newest first, to HTML-escaped notes and answers `[]` for a mod with none.
- **Endorse and track:** only on the user's click, signed in: `POST /v1/games/stardewvalley/mods/<id>/endorse.json` and `abstain.json` with `{version}`; `POST`/`DELETE /v1/user/tracked_mods.json` with `{domain_name, mod_id}`. CLI `mortar nexus untrack` ([HUMANS.md](../HUMANS.md#command-line)). A mod's cached details compared with its `nexus-seen.json` record decide **New** (a mod never looked at is not New; nothing is fetched for it).
- **Files:** `GET /v1/games/stardewvalley/mods/<id>/files.json` lists every file (170 for Content Patcher) with `file_id`, `file_name`, `version`, `mod_version`, `category_name` (`MAIN`, `OPTIONAL`, `UPDATE`, `MISCELLANEOUS`, `OLD_VERSION`, `ARCHIVED`, or null), `size_kb`, `is_primary`. An update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. Before choosing, GraphQL v2 `modFiles { fileId scannedV2 }` is asked: a file whose `scannedV2` is `QUARANTINED` is omitted, and a request for that file id fails the queue item.
- **Download links:** `GET /v1/games/stardewvalley/mods/<id>/files/<file id>/download_link.json`. Premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 ("...this is for premium users only", measured) and needs the `key` and `expires` from the `nxm://` link of the site's Mod Manager Download, one click per mod. Each answer lists several CDN mirrors (`name`, `short_name`, `URI`); Settings › Downloads **Preferred download server** picks one or **Automatic** (empty).

### `nxm://` links

`nxm://<game>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for Stardew Valley (`stardewvalley`) (`internal/nxm/link.go`, `link_test.go`).

- **Registration:** only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`, from Wails' template), taking it from Vortex or Mod Organizer 2. So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees (Windows `HKCU\Software\Classes\nxm`; Linux a user-level `tech.rethunk.Mortar.desktop` with `x-scheme-handler/nxm` and `xdg-mime default`), records the previous handler in `settings.json` (`nxmPreviousHandlers`, `nxmPreviousName`) and restores it when turned off or when uninstall runs `mortar.exe --release-links`. **Send other games' links to …** forwards other games' links to the recorded handler (`internal/nxm/forward.go`).
- **Bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once and handles in order; a link that arrives again before its own `expires` is taken once (the record is in memory).
- **Browser limit:** Chromium browsers launch at most one external protocol per user gesture (`g_accept_requests` in `chrome/browser/external_protocol/external_protocol_handler.cc`), so Nexus Slow Download countdowns that end with no click in between are blocked (`Not allowed to launch 'nxm://…' because a user gesture is required.`).

### Browser extension host

The extension lives in its own repo (<https://github.com/Rethunk-Tech/mortar-browser-extension>, MV3 for Chromium and Firefox; UI in [gui-design.md](gui-design.md#browser-extension)). It avoids the gesture gate: on `www.nexusmods.com` it reads each `nxm://` anchor and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`: Chromium passes the extension origin as the first argument, Firefox the manifest path and extension id). That process starts `mortar <link>`, so the link takes the same second-instance path.

- **Protocol:** every extension message carries `protocol` and every reply carries Mortar's (`nativehost.Protocol`, 2). Mortar answers `MinProtocol`..`MaxProtocol` (2..2; a message without one counts as 0) and refuses others with `protocolError` `extensionTooOld` or `extensionTooNew`, recorded in `extension-contact.json` as `mismatch` for Settings › Downloads. A change to a message's shape bumps both sides. Message and reply shapes: `internal/nativehost/nativehost.go`, `nativehost_test.go`.
- **Data requests** (read-only, Nexus pages only, answered without starting a download): `installed` returns `modIds` (and `brokenIds`, from the cached SMAPI compatibility list) for the last-open profile of the game the Nexus domain maps to; `mod` returns that profile's entry and the other profiles'. The page's game is the Nexus domain, not a hard-coded Stardew id; every reply carries `games` so the extension maps a page's key to the Mortar game id and opens `mortar://<game id>/mod/<id>`. Gray-out-broken needs Mortar installed but not running.
- The extension follows the Download link of Nexus's requirements dialog only when it points at the page's own mod (requirement rows carry links to other mods), because Mortar resolves requirements itself.
- **Host manifest:** on Linux, turning nxm handling on (and every start while on) writes the host manifest into `NativeMessagingHosts/` of each installed Chromium browser under `$XDG_CONFIG_HOME` (Chrome, Chromium, Brave, Edge, Vivaldi) and `~/.mozilla/native-messaging-hosts/`; turning it off removes them (`internal/nxm/nativehost_linux.go`). A Flatpak build writes none (a browser outside the sandbox cannot run it). The unpacked extension's id is fixed by the `key` in its manifest.

### Download queue

An import or a profile's missing files run one queue (`internal/queue`: `queue.go`, `work.go`, `resume.go`, `merge.go`, `overlay.go` and tests), persisted in `<datadir>/queue.json` without `nxm://` keys. **No re-hosting:** mod files and Nexus data stay on the user's machine; a share link holds IDs only. Rules a change must keep:

- Items store as `nexus-<mod id>-<file id>`; the entry records source kind `nexus` with mod id, file id, version, picture URL and endorsement count, fetched once at install.
- **`latest`:** installs started from a save's missing mods, a missing dependency or a Problems fix follow Nexus `file_updates` to the newest listed file, because the file they name came from the dataset or a save and may be old. Share imports leave it off to reproduce the shared files.
- **Which file an update downloads** (`nexus.Supersedes`, `internal/nexus/choose.go`, `update_selection_test.go`): a page can hold several downloads (a main file and optional packs) and its version is the main file's, so the page's version never decides. In order: the author's `file_updates` chain; a newer file of the same download (display name or archive stem); the one current file of the entry's category at the new version; for a MAIN entry on a page with exactly one current MAIN file, that file. When the installed file is the newest of its download the mod has no update, however high the page's number; when none supersedes it but a current file of another download exists the update is marked `pickFile` and nothing queues it. A queued update that resolves to a file the profile already holds ends `skipped` (`queue.skipHeld`).
- **Update to CurseForge:** a mod whose newest version SMAPI reports from a `CurseForge:<id>` update key is resolved through the CurseForge driver (`problems.curseforgeSwitches`): the newest stable file becomes an update of source `curseforge`, marked `switch` with `fromSource` when installed elsewhere; a project that forbids downloads outside CurseForge shows as `notDistributable`.
- Premium accounts download without clicks. A free account's head item waits for its click (**Open download page**, **Skip**) and a matching `nxm://` link is routed to it. A Nexus file the game's store already holds installs from the store with no download and no click, unless the profile has an entry from the same mod page, whose Install together choice needs the archive.
- A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset. An install that unpacks without a SMAPI manifest pauses in `needs-root`; FOMOD and multi-asset releases use `needs-fomod` and `needs-choice` the same way.
- **Resume:** a retry or restart sends `Range` from the partial's size and accepts 206, starts over on 200, and starts over when the `ETag` changed or `Content-Range` mismatches, at most three times; a dead Nexus link is replaced through the download-link call first. GitHub assets always start over, and `Content-MD5` is not checked.
- **Source kinds:** `profile.Source.Kind` is `local`, `nexus`, `github`, `thunderstore`, `modrinth`, `curseforge`, `itch` or `vsmoddb` (`profile.Kind*`), plus `smapi` and `mortar` for bundled entries. A `github` source holds `repo` (`owner/repo`), `tag`, `asset` (share links read them as `<owner>/<repo>@<tag>/<asset>`).

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases` without sign-in. Answers are cached on disk for an hour and served stale when GitHub is unreachable. The unauthenticated limit is 60 calls an hour per IP; a reached limit shows its retry time. SMAPI's own release lookup uses the same client.

**Trust** (`internal/github/verify.go`): a GitHub-sourced install counts as verified only when SMAPI's update API (`includeExtendedMetadata: true`) maps the manifest's `UniqueID` to the same repo. A known mismatch parks the item in `needs-confirm` (Install anyway or Skip); an unknown answer installs and marks it "could not verify"; nothing here blocks.

- **Asset picker** (`internal/github/pick.go`, `pick_test.go`): for a release with several archives the first rule that leaves one wins (the asset shaped like the one the user last chose, kept in `github-choices.json`; else installable assets; else zips one of the game's loaders recognises); several left park the item in `needs-choice`.
- **GitHub vs Nexus for updates:** Update review uses GitHub when the mod's update key is `GitHub:<owner>/<repo>` and SMAPI's suggested update URL is on github.com; otherwise Nexus. A Nexus update carries a GitHub fallback repo (`GitHubFallback`): a free Nexus account must click for every file, so when the item would wait for that click the queue looks for a GitHub release at the same version with exactly one archive. A metadata repo may publish several mods, so the staged archive must contain the updated mod's UniqueID (`FallbackID`), else the item goes back to Nexus. Measured on the main profile: 161 mods carry a metadata repo and 34 have a one-archive release at their installed version.
- When an update check finds a manifest older than the download it came in (the installed file is already the suggested version), Mortar sets that manifest's `Version` to the suggested version in the profile's copy and the store item, so SMAPI stops offering an installed update; a mod from another file of the same entry is never rewritten.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable (Discord community posts 14574789338135 and 25441082215447), so a link is `https://mortar.rethunk.tech/<game id>/p#<payload>`, handed to the app as `mortar://<game id>/p/<payload>`. Each playable game's page is written from `scripts/site/share-page.html` by `scripts/site.ts` (the gate checks it), all running `site/share/app.js`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload.
- **Payload** (`internal/share/share.go`, `share_test.go`): compact JSON `[3, "<profile name>", "<game id>", {"<source id>": "<that source's game key>"}, [<entry>, ...], "<game version>"]`, Brotli quality 11, base64url without padding (`github.com/andybalholm/brotli`, MIT; the standard library has none). The leading number is the format version (only 3 is read); the game version is optional; game keys are stated once per link. The link holds no `UniqueID`s, which barely compress. About 240 mods fit a 2,000-character Discord message. `site/share/testdata/go-link.txt` is the link the app's encoder made, read by both the Go and site tests.
  - **Entry** = object naming its source, so a link names the exact file: `{"s":"nexus","mod":<id>,"file":<id>}`, `{"s":"github","repo":"<owner>/<repo>","tag":"<tag>","asset":"<asset>"}`, `{"s":"thunderstore","ns":"<namespace>","name":"<name>","version":"<version>"}`, `{"s":"curseforge","mod":<project id>,"file":<file id>}`, `{"s":"vsmoddb","name":"<modid>-<assetid>","file":<release id>,"version":"<version>"}`, `{"s":"itch","name":"<user>/<game>"}`, `{"s":"patreon","name":"<post id>"}`. The format version is unchanged for new sources: an older Mortar rejects an unknown source as a bad entry.
  - **Optional extras:** `disabled`, `fomod`, `note`, `tags`, `files` (a split archive's per-file `note` and `tags`), `overlay` (`from`, `to`, `off`), `imp` (implicit entry), `pin`/`pinr`, `grp` (profile group names); for the share page `kb` (store item size, two significant digits) and `min` (newest `MinimumGameVersion`). When a link would pass the cap, `kb` and `min` go first, then the extras except `imp`. A share with no `imp` entry may predate install reasons, so the receiver infers them (a listed package another listed package requires is implicit; members of a cycle nothing outside requires stay explicit); profile codes, `.r2z` files and Thunderstore modpacks are inferred the same way.
  - **What is shared:** only enabled entries with a source; local archives and switched-off entries are listed at Share as left out. Every entry cut from one store item is one ref keyed by `Entry.StoreKey()`, carrying the switched-off entries' ids in `disabled`. SMAPI's bundled mods and the bridge are never shared, listed or imported (every profile gets them from the signed component manifest).
  - **On the receiver:** CurseForge downloads with the receiver's own key (without one the preview lists it unavailable, `sharesvc.ReasonCurseForgeKey`); itch.io and Patreon entries travel as the page alone. Optional files are entries like any other, installed after their main file (`Request.Overlay`). The share page shows pictures only where public, keyless URLs follow from the link (Nexus thumbnail URLs are too long to carry: a 644-mod profile's link already used 5 KB of the 8 KB).
- **Share dialog and import** (`internal/sharesvc`, `preview.go`, `frontend/src/share`): the dialog shows a length meter against 2,000 characters and suggests the file over 240 mods or the 8 KB payload cap. Import preview resolves every entry and creates nothing: a Nexus file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version, else the primary file ("different file"); a mod with no files or a 404 is unavailable. Nothing downloads before the user's click on **New profile from link** or **Add to the selected profile**.
- **`.mortar` file:** a zip holding `profile.json` (same format version and entries as a link, the game and its source keys, name, notes, description and the shared mods' ids `ids`, which bound the config files it may carry), `configs/<format>/<local id>/<relative path>.json` for each enabled mod's `.json` files except `manifest.json`, and `loader/<path in the profile>` for text config files (`.cfg`, `.json`, `.toml`, `.ini`, `.yml`, `.yaml`, `.txt`, valid UTF-8) under the config folders of the loader the profile runs (`loader.WithConfig`), leaving out the companion's state file. Files over 1 MiB, with unusual names or past the totals are skipped and listed at Save. The description (at most 280 characters) travels only in this file; colour and icon travel in neither.
  - Config files are written by `share.Apply` once their mods are installed: only under a folder an installed mod of that import already has, re-validated at write time, never over mods the profile already had; waiting ones are kept in `<datadir>/pending-configs.json` independently of queue rows, and apply waits for the game to go idle.
  - **Problem choices** (`problems` in `profile.json`; File and LAN only): `dismissed` tokens and `wins` (a pack that loads after a loser: `Component.LoadAfter`), caps 1,000 of each with tokens at most 300 bytes; a file past them is refused whole. The receiver only adds (`sharesvc.applySharedChoices`, `choices.go`) and skips a win when the profile decided the pair the other way.
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml` and `.mortar` in `fileAssociations:`; on Linux `nxm.System.RegisterLinks` writes `~/.local/share/mime/packages/mortar.xml` for `application/x-mortar`, keeps the user desktop entry and sets both `xdg-mime` defaults. A link reaches the app as `events.Common.ApplicationLaunchedWithUrl` on a cold start (fired when the only argument contains `://`, `Rethunk-AI/wails` `v3/pkg/application/application_linux.go:73-83`) or in `SecondInstanceData.Args` when running; `sharesvc.Receive` also reads `.mortar` paths and `file://` URLs (including Windows UNC). A link or file opens the Import dialog filled in, never importing by itself. `mortar://<game>/mod/<id>` (a positive decimal Nexus mod id with no leading zeros, no query or fragment) selects the Nexus mod on the Mods tab (`route.go`, `route_test.go`).
- **Trust boundaries:** link parsing accepts only the known forms and caps the encoded payload at 8 KB and the decompressed at 64 KB before parsing; a `.mortar` file is capped at 32 MiB, 5,000 entries, 1 MiB per config and 32 MiB of configs, and any entry outside its layout fails the whole file; the clipboard is read only when the user presses Paste. Extraction limits: [Trust boundaries](#trust-boundaries).
- **LAN sharing** (`internal/lan`): with Settings › General **Share profiles on the local network** on, Mortar advertises `_mortar._tcp` (hashicorp/mdns) and serves HTTP on `lanPort`; sends are refused while sharing is off and incoming shares are rate-limited per peer (10 s). A send is a `.mortar` payload (at most 32 MiB). To a paired computer every option applies and archives added from disk travel as store items; to an unpaired one config files are dropped (they can hold keys) and local archives left out. Handshake protocol 5. UI: [gui-design.md](gui-design.md#profile-management).
  - **Pairing** makes two of the user's own computers trust each other, independent of any store account: a single-use code (8 characters, valid 5 minutes) shown on one and typed on the other, leaving a 32-byte key in `<data>/lan/peers.json` (0600). Exchange (`POST /pair/begin`, `/pair/finish`): X25519 from both sides, then HMAC proofs over the transcript (which binds both devices' names) and the X25519 secret keyed by a PBKDF2 stretch of the code (200,000 rounds), so a passive observer cannot test code guesses; the long-term key is HKDF of the X25519 secret, never of the code. A host locks a peer for 10 minutes after 5 wrong codes and burns the code after 15. Threat model: comment at the top of `internal/lan/pairing.go`.
  - **Share handshake** (`protocol.go`, `service.go`, `paired_import_test.go`): the sender `GET`s `/hello` (receiver's id and a one-minute nonce bound to that peer) then `POST`s `/share` with the payload, its port, its id and, when the receiver is paired, an HMAC-SHA256 proof under the pairing key over the nonce concatenated with SHA-256 of the payload (hex); the key is never sent. A paired proof marks the share **paired**: the response carries a 5-minute Bearer token scoped to the store keys of every entry, with a proof under the same key so the sender never grants a token an unpaired computer made up.
  - **Store transfer** (`transfer.go`): the receiver `GET`s `/store/<game>/<key>` with that token and the sender streams a tar of each granted store folder (10,000 entries and 2 GiB caps). Invariant: the receiver installs through `Store.AddDir` only when the hash of what arrived (`store.HashDir`) equals the one the sender vouched for, and refuses an entry with no vouched hash; a paired share lists per entry the folder's hash with an HMAC over game, entry key and hash (`entryDigests`, protocol 4), so what an eavesdropper serves on the unauthenticated transfer address cannot pass for what the sender holds. Sending between one's own machines is copying, so a paired receiver gets the files whatever the source or licence.
- **Windows firewall:** the per-user installer adds no firewall rule. Settings › General **Fix** relaunches Mortar elevated (`--firewall-allow`), which writes the rules through `INetFwPolicy2` (`internal/lan/firewall_windows.go` `AllowFirewall`): it removes every inbound block rule for the executable (Windows names the ones it creates after the file description, not `Mortar`) and writes a rule for every network profile so Windows never prompts. Default: allow on Domain and Private with an explicit block on Public; with the allow-any-address setting: allow on every profile. When every connected network is Public and the setting is off, Mortar does not listen and LAN use returns a Permission error (`publicBlocksListening`, `errPublicNetwork` in `internal/lan/firewall.go`).
- **Nexus collection draft** (`sharesvc.ExportCollection`, `collection_export.go`, `collection_export_test.go`): read-only (no Nexus write). One `collection.zip` holding `collection.json` in Vortex's `ICollection` shape ([`ICollection.ts`](https://github.com/Nexus-Mods/Vortex/blob/master/src/renderer/src/extensions/collections/types/ICollection.ts)), using the importer's Go types so `parseChoices` reads an export back. Nexus entries are `source.type: "nexus"` with `modId`, `fileId`, `updatePolicy: "exact"`; a GitHub asset is a `direct` source, a local archive a `manual` source; each enabled mod's `.json` files go under `bundled/<local id>/`. Mortar cannot fill `info.author`/`authorUrl`. Nexus takes a collection as a 7z, and no 7z-writing Go library is in go.mod (`bodgit/sevenzip` is read-only), so the export is a zip and the toast gives a one-line repack to 7z.

## Sync folder

`internal/syncsvc` keeps each profile's state in step between computers through a folder that another tool (Syncthing, Dropbox, a NAS) carries. It carries the profile's `.mortar` export (never mod files, so every computer downloads each mod from its source). The folder is the `syncFolder` setting (empty is off); `main.go` runs the service with a five-second quiet period.

- **Layout:** `<folder>/<game>/<remote id>.mortar` is the payload and `<remote id>.sync.json` the version file `{name, machine, machineName, vector}`; the vector maps a machine id to the newest revision that machine wrote. The payload is written first and the version file last, so a computer that sees a version finds the payload it names. Local state `<data>/sync-state.json` holds this machine's random id and, per local profile, its remote id, the vector last written or applied and the profile's `updated` time then.
- **Offers** (`syncsvc.go`, `property_test.go`): a version file whose vector holds a revision this machine lacks becomes an **offer**, never merged. `Resolve(game, remote, "theirs")` makes the profile match the payload through the share service's replace and adopts the remote vector; `"mine"` keeps the local profile and writes a revision on top of both vectors. A profile changed on both sides is flagged `Conflict`; the offer list is emitted as `sync:offers` only when it changes.

## Release

Build and publish mechanics live in `Taskfile`/`build/` and [HUMANS.md](../HUMANS.md#release) (workflow, how `wails3` is built from the fork, the update key); facts that settle questions:

- **Linux artifacts:** AppImage (`wails3 task linux:create:appimage`; AppRun sources `build/linux/appimage/glibc-check.sh`, because the bundled WebKitGTK and GTK 4 need host glibc 2.38 or newer: an older host gets a dialog pointing to the Flatpak); nfpm `.deb`/`.rpm`/Arch (`wails3 task linux:nfpm`) from a binary linked with `-X main.packaged=deb`; a Flatpak bundle (`wails3 task linux:flatpak`, built with `--runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo` so the bundle can fetch its runtime; GNOME Platform/SDK 50); the packaged ELF (`bin/mortar-aur-linux-amd64`/`-arm64`) for the AUR `mortar-bin` PKGBUILD (`build/linux/aur/`); and the AppImage's unpackaged binary as portable `bin/mortar-linux-amd64`/`-arm64`, which updates itself and writes its own desktop entry and nxm handler. amd64 and arm64 both ship; Stardew Valley has no native ARM Linux build and runs through Box64 or FEX there.
  - The package remove script (`build/linux/nfpm/preremove.sh`, skipped on upgrade) runs `mortar quit`, `--release-links` and `uninstall-cleanup` as the user who ran the package manager through sudo or pkexec (per-user state is out of root's reach otherwise); `uninstall-cleanup` also removes the autostart entry, profile desktop entries, the user desktop entry, icons, MIME definition and defaults, unless that entry runs another Mortar copy that still exists.
  - **arm64:** CI runs it only on `v*` tags (`ubuntu-24.04-arm`); local arm64 deb/rpm/Arch are `wails3 task linux:build:arm64` (arm64 .debs extracted into `tmp/linux-arm64-sysroot`, then `zig cc -target aarch64-linux-gnu.2.39`); the AppImage stays CI-native because linuxdeploy-aarch64 needs qemu plus a full runtime.
- **Flatpak sandbox:** finish-args (`build/linux/flatpak/tech.rethunk.Mortar.yml`, copied into the Flathub manifest by `build/linux/flathub/render.sh`) expose Heroic and Lutris config (read-only), default GOG and Heroic install folders and Flatpak Lutris/Heroic data (read-write, for SMAPI), native and Flatpak Steam libraries and Mortar's data folder. Other paths are invisible until `flatpak override --user --filesystem=<path> tech.rethunk.Mortar`.
  - **Host access** (`internal/sandbox`, `FLATPAK_ID` set): the sandbox cannot see the host's Steam, processes or session folders, so Mortar goes through `flatpak-spawn --host` (finish-arg `--talk-name=org.freedesktop.Flatpak`); every launch runs on the host with `--directory` and `--env`, so the game never inherits the sandbox and the manifest needs no audio socket or `--device=all`.
  - **Portals:** launch at login uses the Background portal (`internal/portal`); profile shortcuts the DynamicLauncher portal, which writes `flatpak run` into each entry so the sandbox needs no write access to host folders. Add to Steam is refused in the Flatpak (host Steam cannot start `/app/bin/mortar`), with an error naming `flatpak run tech.rethunk.Mortar --play=<game>/<profile> --steam-session`.
- **Windows:** a per-user NSIS installer is the only scope (`build/windows/nsis/wails_tools.nsh` `WAILS_INSTALL_SCOPE`), installing to `$LOCALAPPDATA\Programs\Mortar` without admin (a machine-wide build would register a second copy beside it); the updater's Windows asset is the bare `mortar-windows-amd64.exe`. Before the installer copies files or the uninstaller removes them, both close a running Mortar: `mortar quit` asks the app at `$INSTDIR` to close over its control channel (`app.quit`: replies with its pid, or refuses with the reason when downloads or the game run unless `--force`) and waits until the pid has exited, failing after ten seconds. The signed manifest lists both Linux AppImages plus the Windows exe so the updater matches `runtime.GOARCH`.
- **Self-update:** `internal/updatesvc` drives Wails' updater (`app.Updater`) with the `endpoint` provider reading the signed manifest at `https://github.com/Rethunk-Tech/mortar/releases/latest/download/manifest.json`; signing key `main.go` `updateKey` (the private half never enters the repository). Wails' GitHub provider is not used because it verifies no signature, only an optional checksum asset.
  - **Flow:** a production AppImage, portable Linux binary or Windows build checks in the background (after startup, then every four hours), downloads and verifies a newer signed release without prompting and leaves it staged; quitting applies it. A release is installed only when its manifest entry carries a signature. Asset URLs name the release tag (`releases/download/v<version>/…`), so a release published mid-update cannot swap the file under it.
  - **Off:** a build without the `production` tag (`wails3 dev`), a server build, a version containing `dev`, or a packaged build (`-X main.packaged=…` from nfpm, Flatpak, AUR). The bare Linux binaries are listed in the manifest under platform `linux-portable` (`updatesvc.PortablePlatform`; `release:manifest` rewrites their inferred `linux`, which the per-file signatures do not cover), so each flavour replaces itself with its own kind of file.
  - **Test:** `task test:updater` (Linux) builds two server-mode copies of `internal/updatesvc/testdata/fixture` (0.1.1, 0.1.2), serves a manifest signed by `wails3 updater manifest` and asserts the binary becomes 0.1.2 and relaunches, while a tampered artifact, a wrong-key signature, an unsigned entry and a downgrade manifest are refused; a further case runs from a fake `$APPDIR` with `$APPIMAGE` naming a separate file and asserts that file is replaced. The build tag `updatetest` (never in releases) lets `MORTAR_UPDATE_MANIFEST_URL` replace the manifest URL.
  - **Windows swap** (`applied_windows.go`: the old exe is renamed `.old.<n>` because a running exe cannot be deleted) is not in the automated test; measured in the Windows 11 VM with both builds from one commit, a test key and `-tags updatetest`: the NSIS user-scope 0.2.2 found 0.2.3 on its first background check, **Restart now** replaced `%LOCALAPPDATA%\Programs\Mortar\mortar.exe` and relaunched 0.2.3, the new process removed the `.old.<n>` copy (`RemoveOldExecutables`) and `DisplayVersion` under `HKCU\…\Uninstall\Rethunk.TechMortar` went from 0.2.2 to 0.2.3.
- **What's new:** `<datadir>/last-run-version` records the previous run's version; when the running version is newer, Mortar fetches that release's GitHub notes once and shows them; dismissing writes the current version; offline skips silently and leaves the file so the next start tries again.
- **Fork patches** (`Rethunk-AI/wails` branch `mortar/v3.0.0-beta.30`):
  - **Self-contained AppImage** (`v3/internal/commands/appimage.go`; offered upstream on wailsapp/wails#6213 as `fix/v3-appimage-webkit-sandbox`): each WebKit helper directory moves to `usr/lib/<name>` in the AppDir and the bundled library's compiled-in path becomes `././<name>/`, NUL-padded to the same length. AppRun runs the app from `$APPDIR/usr/lib` with the user's folder in `OWD` (Mortar resolves relative launch arguments against it: `sharesvc.LaunchDir`), so the relative path resolves outside and inside WebKit's bubblewrap sandbox, which sees the AppImage's `usr/lib`. The file search covers only `/usr/lib`, `/usr/lib64`, `/usr/libexec` (branch `fix/v3-appimage-gtk-search-roots`), so other projects' AppDirs under `/usr/local` are never bundled. The injected-bundle path stays absolute because bwrap bind-mounts it, so WebKit logs one missing-bundle warning per start.
  - **Updater** (`v3/pkg/updater`): staging goes beside the target and a cross-filesystem rename falls back to a copy (`/tmp` is tmpfs on Fedora); inside an AppImage the updater replaces and relaunches `$APPIMAGE`, not the read-only mount; `Config.OnUpdateApplied` runs once after an update, which Mortar uses on Windows to rewrite `DisplayVersion` under the installer's `UNINST_KEY`, leaving a portable copy without that key alone.
- **Linux desktop integration:** packaged installs (nfpm, AUR, Flatpak) own the system desktop entry `tech.rethunk.Mortar.desktop` (`Exec=mortar %u`, `MimeType` for `mortar://`, `application/x-mortar`, `nxm://`), install the MIME XML under `/usr/share/mime/packages` and ship hicolor icons; a packaged binary (`-X main.packaged=` / `-X …/internal/nxm.packaged=`, `deb` or `flatpak`) writes no user-level desktop entry, icons or MIME XML at startup, and turning nxm on still runs `xdg-mime default` against that desktop id except inside Flatpak. Nothing installs an AppImage's embedded `.desktop` file, so an AppImage writes its own.
  - Application id and single-instance id are both `tech.rethunk.Mortar` (`Options.Linux.ApplicationID`: Wayland `app_id`, X11 `StartupWMClass`), so Wails' D-Bus name `tech.rethunk.Mortar.SingleInstance` sits under the app id, which a Flatpak may own without a finish-arg; a portable copy appends a hash of its data folder.
  - `Exec=` is `$APPIMAGE` when running from that AppImage's mount (desktop files do not expand variables and the mount vanishes on exit); a production build rewrites the entry at startup when its `Exec` target no longer exists; every non-packaged start refreshes the user icons once an entry exists (`Refresh` in `internal/nxm/handler_linux.go`).
- **Download page:** `site/download/index.html` (same static site as the share page); assets `https://github.com/Rethunk-Tech/mortar/releases/latest/download/<asset>` for `mortar-linux-x86_64.AppImage`, `mortar-linux-aarch64.AppImage`, `mortar-windows-amd64.exe`, `mortar-amd64-installer.exe`. `bun run site:downloads` (`scripts/site-downloads.ts`) resolves every release link on the site against the latest releases and fails on a missing or mismatched asset; CI runs it when `site/` changes and `release.yml` after publishing.
